Mission 指南

mission-band：掛在輸入框上方的任務進度提示。這份教學頁給第一次用的人看。

這是什麼

mission-band 是顯示在輸入框正上方的一條任務進度提示。它只做兩件事：顯示目前走到哪一步、在該提醒的時候提醒； 不會幫你操作、也不會卡住你繼續對話或打指令。進度是從實際發生過的事情推算出來的——打過哪個指令、讀過哪個檔案、 跑過哪個 git 或 glab 查詢——不是靠 AI 自己回報「這一步我做完了」。這樣就算你中途換了一個全新的對話， 只要任務還綁在同一個 worktree 或 session，band 一樣看得到正確的進度。

重裝或交接給別人時，安裝步驟和前置條件見 mod 目錄的 README.md。

五分鐘上手

一個功能從頭走到尾的標準路徑；下面先看一段示意動畫，再看每一步要打什麼。

○●✓ 開始 ○●✓ 實作 ○●✓ 驗收 ○●✓ 審查 ○●✓ 收尾
○▶✓ 步驟 A
○▶✓ 步驟 B
○▶✓ 步驟 C

示意：階段 tab 依序前進、步驟從 ○ → ▶ → ✓（循環播放；偏好減少動態效果時停在單一畫面）。

開始
/mission-start #473

有對應的票就帶票號；沒有票就 /mission-start 一個名稱。

細節

任務名稱會自動變成「月日-#473」這種格式。

開始

「開始」階段照順序打：

/grill-with-docs把需求問清楚 → /approach檢查要用套件還是手寫 → /prototype可跳過 → /to-spec整理成規格 → /to-acceptance產驗收清單 → /to-tickets票數多才打，可跳過 → orca worktree create跟 AI 說、請它建（不要加 !）；之後 /mission-go 開新分頁
實作
/mission-next

進入「實作」階段；任務綁在主 checkout 的 session 才會提示下一步。

細節

如果任務綁在主 checkout 的 session，/mission-next 的回覆文字會提示打 /mission-go 開一個新分頁（自動接到 worktree，而且會自動幫你打 /mission-restore 接回任務，不用自己再打一次）。

實作
/mission-restore #473

只有自己手動開新分頁、或 orca 啟動失敗時才需要打；接回之後照 TDD 開始實作、commit。

實作
/pstack:no-comments

清這個分支的註解，接受的問題也會直接改 code 修掉。

細節

除了刪註解，MUST KILL 問題會直接改 code（可能跑一次 /architect 先定形狀），確定要留的限制會停下來等你核准要不要編碼進型別或測試；理由要留文字照本專案規則縮成 issue 連結或寫 ADR（見下方 FAQ）。舊任務不需要就 /mission-skip no-comments 理由；要在 code review 之前跑，審查才看到乾淨的程式碼。

實作
/mattpocock-skills:code-review

改動大或風險高改用 /cr。

細節

要 Codex 再審一次就 /codex:rescue，不需要就 /mission-skip code-review:codex 理由。

驗收
/mission-next → /verify-acceptance

進入「驗收」階段，逐條跑完驗收清單，回歸測試跟整體回歸也在這裡做完。

審查
/mission-next → /push

進入「審查」階段，打 /push 開 MR（spec 會自動凍結到 issue 留言）。

細節

同事看過之後打 /mission-review 同步核准、回饋，該重驗、該 push、該回覆就照 band 的下一步做；MR 真的合併時，/mission-review 會自動帶你進「收尾」階段（沒自動進才需要自己打 /mission-next）。

收尾
/retro

進了「收尾」階段，回顧這次 session。

收尾
/mission-finish

清掉這個任務的紀錄。

細節

MR 沒合併就被關掉的話，改用 /mission-finish 名稱 --force。

收尾
/cleanup

任務紀錄清掉之後，刪掉 worktree 和分支。

細節

在主 checkout 要帶分支名或 #issue：/cleanup <分支> 或 /cleanup #<issue>。

不確定現在卡在哪一步，隨時看 band，或打 /mission-log 看這個任務記錄過的所有事件。

流程總覽

五個階段由左到右，底下依序是這個階段要做的步驟；手機寬度請左右滑動查看。

怎麼看 band

視窗夠寬（100 欄以上）時，band 會畫成兩個框：左邊「步驟」、右邊「資產」。例如審查階段走到第 3 輪：

demo > 1025-#473｜✓ 開始 ✓ 實作 ✓ 驗收 ● 審查（第 3 輪） ○ 收尾｜上次同步 2 小時前    h: ?
⚠ 連續幾輪在修上一輪的修法，先停下來檢查前提
╭ 步驟 ─────────────────────╮╭ 資產 ──────────────────────╮
│ ✓ open-mr                 ││ • #473             issue    │
│ ✓ freeze-spec              ││ • !493              MR      │
│ ○ await-review             ││ • GLOSSARY.md       文件    │
│ ○ verify-acceptance/overall││                              │
│ ○ push-fix                 ││                              │
│ ○ reply                    ││                              │
│ ○ approved                 ││                              │
╰────────────────────────────╯╰──────────────────────────────╯
下一步：等同事看過之後，跑 /mission-review 同步 MR 狀態

每個部分對應：

第一行
階段 tab。✓ 已經走過的階段、● 目前階段（粗體）、○ 還沒到的階段。審查階段第 2 輪起會附「（第 N 輪）」；同一行最後面可能還有「上次同步 X 前」（只在審查階段、同步過才顯示）。60 欄以上才會在最右側留一顆 h: ? 說明按鈕，不到 60 欄縮成單行時沒有按鈕，開教學頁要用 /mission-help。
⚠ 開頭
警示列。常見三種：票數有變動要不要同步 issue 描述、規格改過要不要更新驗收清單、連續第 3 輪起都在修上一輪的修法該停下來檢查前提。
步驟框
目前階段每個節點的狀態。塞不下全部節點時，前面已完成或略過的會先收成一行「前面 N 項已完成或略過」；再塞不下就從後面截斷，顯示「另有 N 列」，目前卡住的那一步一定留著不會被擠掉。有些節點會在後面附進度細節，例如驗收階段的 verify-acceptance 可能顯示「AC 5/8，1 未過，2 受阻，1 後補」：後補是受阻、但驗不了時標了可後補的 AC，不擋這個節點。
資產框
這個任務收集到的連結（issue、MR、Figma、GLOSSARY.md 等），可以直接點開。還沒有資產時顯示提示文字，可以用 /mission-link 手動加。
最後一行
下一步該做什麼的提示文字。

步驟框裡每個節點的符號：

○
還沒開始
▶
進行中（已經有對應的事件，但還沒算完成）
✓
完成
✗
被跳過（/mission-skip 手動跳過，或節點自己判斷不需要）

只有「對應事件」是指真的能偵測到的動作——打過某個 skill、讀過某份文件、跑過某個 Bash 指令——這類節點沒做完才會顯示 ▶。 完全靠 git 或 GitLab 狀態判斷完成與否的節點（例如 await-review、push-fix、approved）沒有這種中間事件， 沒做完一律是 ○，不會變成 ▶；一旦條件成立就直接變成 ✓。

寬度規則：不到 60 欄縮成一行摘要（沒有「?」按鈕）；60–99 欄只畫步驟框（沒有資產框，但有「?」按鈕）；100 欄以上兩框並排。高度最多 13 列，塞不下時一樣會退回單行摘要。

五個階段與每個步驟

流程固定五個階段：開始 → 實作 → 驗收 → 審查 → 收尾。下面每張表列出這個階段的節點、該做什麼、怎麼算完成、不需要時怎麼跳過。

開始
步驟做什麼怎麼算完成不需要時
grill-with-docs打 /grill-with-docs，把需求問到能拿來驗收偵測到打過這個 skill必做；沒做完會擋 /mission-next，真的不需要可 /mission-skip grill-with-docs 理由
approach打 /approach，檢查要用套件還是手寫、放哪裡、介面形狀、從哪裡開始偵測到打過這個 skill必做；沒做完會擋 /mission-next，真的不需要可 /mission-skip approach 理由
prototype（選用）有要做的設計決定才做 prototype打過 /prototype，或讀過它的 playbook選用節點：沒碰過不會擋路，也可以 /mission-skip prototype 理由
to-spec在同一段對話打 /to-spec，把討論整理成規格偵測到打過必做；沒做完會擋 /mission-next，真的不需要可 /mission-skip to-spec 理由
to-acceptance打 /to-acceptance 產生驗收清單驗收清單檔存在舊任務不需要就 /mission-skip to-acceptance 理由
to-tickets（選用）票數多才拆票；小票可以跳過打過 /to-tickets選用節點：沒碰過不會擋路
create-worktree請 AI 用 orca 或 git worktree add 建 worktree（不要用 ! 自己跑）從 AI 跑的指令偵測到 worktree 路徑（orca 的 JSON、--name 對 git worktree list，或 cd 進 worktree）必做；沒做完會擋 /mission-next，真的不需要可 /mission-skip create-worktree 理由
實作
步驟做什麼怎麼算完成不需要時
implement照 TDD 或打 /implement 開始寫 code偵測到 commit必做；沒做完會擋 /mission-next，真的不需要可 /mission-skip implement 理由
no-comments打 /pstack:no-comments，清註解並直接修正接受的問題（可能改 code，確定要留的限制會等你核准才編碼）偵測到打過這個 skill，或讀過它的 SKILL.md必做；沒做完會擋 /mission-next，真的不需要可 /mission-skip no-comments 理由
code-review（兩軌）Claude 軌道打 /mattpocock-skills:code-review（或 /cr）；Codex 軌道打 /codex:rescue 或直接跑 codex exec兩條軌道各自「跑過或被跳過」就算完成（不是只有 Codex 可以跳，兩邊規則一樣）可以只跳 Codex 軌道、只跳 Claude 軌道，或整個節點一起跳：/mission-skip code-review:codex 理由、/mission-skip code-review:claude 理由，或 /mission-skip code-review 理由
驗收
步驟（顯示名 / 跳過用的 id）做什麼怎麼算完成不需要時
verify-acceptance / acceptance-run打 /verify-acceptance 逐條跑驗收清單每條 AC 都是通過，或後補（受阻且驗不了時標了可後補）舊任務沒有清單：/mission-skip acceptance-run 理由
verify-acceptance/regression / regression-write幫「回歸：是」的 AC 補寫回歸測試清單上標記「回歸入庫：已寫」沒有要進回歸的條目就不擋路，不用手動跳
verify-acceptance/overall / overall-regressioncommit 之後跑一次整體回歸清單記的整體回歸狀態是「通過」，而且記的 SHA 等於目前 HEAD（兩個條件都要成立）沒有驗收清單的舊任務：/mission-skip overall-regression 理由
blast-radius讀 pstack 的 blast-radius 判準，確認改動波及的範圍讀過那份文件必做；沒做完會擋 /mission-next，真的不需要可 /mission-skip blast-radius 理由
interrogate（選用）不確定自己講不講得出改動原因就讀 pstack 的 interrogate讀過那份文件有把握可以跳過，不碰也不擋路
審查
步驟做什麼怎麼算完成不需要時
open-mr打 /push 開 MR偵測到本專案的 MR 網址必做（這個階段的節點不會直接擋 /mission-next，見下方備註）；真的不需要可 /mission-skip open-mr 理由
freeze-spec/push 開完 MR 會自動把 spec 凍結到 issue 留言；已經開過就再跑一次 /push 選「僅推送」補發偵測到對任務 issue 留言沒有對應 issue 或 spec：/mission-skip freeze-spec 理由
await-review等同事看過之後打 /mission-review 同步同步到第一則別人的回饋，或 MR 已經 approved必做（這個階段的節點不會直接擋 /mission-next，見下方備註）；真的不需要可 /mission-skip await-review 理由
verify-acceptance/overall / reverify（顯示名跟驗收階段那個相同，但是不同節點）改完 code 或 rebase 之後要重跑整體回歸整體回歸狀態是「通過」，而且記的 SHA 等於目前 HEAD自動視為跳過：從來沒有整體回歸紀錄，或驗收階段本來就 /mission-skip overall-regression 跳過了；一般不用手動跳
push-fix本機跟遠端不一致就要 push；rebase 過要 force-push，自己用 ! git push --force-with-lease 執行遠端分支 SHA 等於本機 HEAD必做（這個階段的節點不會直接擋 /mission-next，見下方備註）；真的不需要可 /mission-skip push-fix 理由
reply逐則回覆或標 resolved；要用 glab api 發才算，貼在留言框不算本輪回饋都已回覆或 resolved，或最後一則是自己必做（這個階段的節點不會直接擋 /mission-next，見下方備註）；真的不需要可 /mission-skip reply 理由
approved打 /mission-review 同步核准狀態MR 已經 approved必做（這個階段的節點不會直接擋 /mission-next，見下方備註）；真的不需要可 /mission-skip approved 理由
收尾
步驟做什麼怎麼算完成不需要時
retro打 /retro 回顧這次 session偵測到打過必做；band 會一直提醒，但到了「收尾」階段後 /mission-finish 不會因為這步沒做而擋（只看階段是不是已經到最後），真的不需要可 /mission-skip retro 理由
correct（選用）不確定就讀 pstack 的 correct讀過那份文件有把握可以跳過

審查階段比較特別：不是節點全做完就能進收尾，是看 MR 真的合併了沒（/mission-review 同步出來的事實）。 節點全做完但 MR 還沒合併一樣會卡住；MR 被關閉沒合併，改走 /mission-finish 名稱 --force。

指令速查

指令參數做什麼
/mission-start#<issue> | <名稱>開始追蹤一個任務流程（名稱自動加日期）
/mission-list-列出所有任務
/mission-restore#<issue> | <名稱>把任務接到這個 session 或 worktree
/mission-skip<nodeId>[:<track>] <理由>跳過目前階段的一個節點，或雙軌節點（如 code-review）底下的一條軌道
/mission-next-進入下一個階段
/mission-go-在任務的 worktree 開新 claude 分頁並接回任務
/mission-review-同步審查階段的 MR 狀態、核准、討論回饋
/mission-finish[名稱] [--force]清除綁定在這裡的任務
/mission-log-列出綁定在這裡的任務事件
/mission-link<標籤> <網址>手動加入或覆蓋一筆資產
/mission-unlink<標籤>刪除一筆資產
/mission-cost[#<issue> | <名稱>] [--sessions <id>,<id>]量任務各階段的 token 用量（/mission-finish 也會先量一次）
/mission-help-開啟這份教學頁；跟 band 右上角「?」按鈕、聚焦 band 後按 h 效果一樣

常見情境 FAQ

任務綁在主 checkout 還是 worktree，有什麼不一樣？

在主 checkout 打 /mission-start，任務是綁在這個 session；在 worktree 目錄裡打，任務是綁在那個路徑。 綁 session 的任務，每次 /mission-next 的回覆文字都會提示打 /mission-go 開一個新分頁， 自動接到 worktree 並幫你打好 /mission-restore；綁路徑的任務不用這一步，留在原來的分頁開發就可以。

換階段要不要 /clear？

任務綁在 worktree 路徑時，/mission-next 會建議先 /clear 再開始：每次呼叫模型都要重讀整段對話， 越後面的階段越貴，而且各階段要接的資料都在 spec、驗收清單跟任務紀錄裡，不靠對話記憶接續。需要帶著前面的討論就改用 /compact。唯一的例外是進入「收尾」階段前：這裡反而會提示先不要 /clear，因為 /retro 要回顧的就是這段對話本身。

某個步驟卡住了，想跳過怎麼辦？

打 /mission-skip <nodeId> <理由>。nodeId 用的是節點 id，不一定跟 band 畫出來的顯示名 一樣（例如驗收階段畫出來是「verify-acceptance」，但 id 是 acceptance-run；完整對照見上面「五個階段與每個步驟」）； 照 band 顯示的名字打也會被接受，mission-band 會自動換成對應的 id。雙軌節點（例如 code-review）要跳過其中一軌時， 格式是 <nodeId>:<track>，例如 /mission-skip code-review:codex 這次不用 Codex。

MR 被關閉、沒有合併，要怎麼收尾？

這種情況任務會停在「審查」階段，不會自動進「收尾」。改用 /mission-finish <名稱> --force 強制清除， 不需要先把所有節點都做完。清掉之後再打 /cleanup 刪掉 worktree 和分支。

任務紀錄清掉了，worktree 和分支要怎麼刪？

/mission-finish 只清任務紀錄，worktree 和分支還留著；回覆文字會提示接著打 /cleanup， 在主 checkout 要帶分支名或 #issue（/cleanup <分支> 或 /cleanup #<issue>）。

band 顯示「另有 N 列」是什麼意思？

代表目前的視窗高度塞不下全部步驟（或全部資產）：已經完成或略過的步驟會先收合成一行，還是塞不下才從後面截斷， 目前卡住的那一步一定留著不會被擠掉。/mission-log 列的是事件紀錄，補不回被截掉的那幾列。 步驟被截時，把終端機拉高可以看到更多（band 最多畫 13 列，拉寬不會多出步驟列）；資產超過上限時， 用 /mission-unlink 清掉不需要的資產，排到前面的就看得到了。

怎麼量這個任務花了多少 token？

打 /mission-cost，可以選帶 #<issue> 或名稱指定任務；如果任務綁定的 session 沒有自動記到 （例如很舊的任務），補 --sessions <id>,<id> 自己指定。/mission-finish 收尾時也會先 自動量一次、附在回覆裡。

no-comments 這步在做什麼？

打 /pstack:no-comments 會丟給 Comment Sicko 子代理審這個分支的 diff；留言只留五種——授權聲明、 外部依賴逼出的怪行為、// prettier-ignore（lint suppression 只在規則本身有問題、太囉嗦或只管風格時才留）、 公開 API 的 doc comment，以及解釋程式碼表達不了之限制的 issue／RFC 連結，其他一律刪。 範圍預設是比對 base 分支（預設 main）加上 working tree；從 rc/* 切出來的 hotfix 分支不是 比 main，打指令時要自己把要比對的 base 講清楚。

不只刪註解：接受的 MUST KILL 問題會直接改 code（改名、抽函式、補型別，或做最小範圍的根因修正）， 形狀需要設計時會先跑一次 /architect；確定要留的限制會提議編碼進型別、執行期檢查、測試或 lint， 並停下來等你互動核准，核准才編碼，否則刪掉並回報這條限制還開著。想留文字說明理由的話，照本專案規則 （見 comment-policy.md）縮成一行 issue 連結，或跨票的決定寫成 docs/adr/ 的 ADR—— 這是我們自己的慣例，不是 pstack 本身要求的。排在 code-review 之前，是為了讓 Claude／Codex 審查時看到的是 清乾淨的程式碼。

這份教學頁要怎麼打開？

三種方式效果一樣：點 band 標題列最右側的「?」按鈕；或先用 ctrl+x tab（或點一下 band）讓它拿到鍵盤焦點， 再按 h（在一般的輸入框裡按不到，要先讓 band 拿到焦點）；或直接打 /mission-help。 開啟失敗（例如不是 macOS，沒有 open 這個指令）時會回傳檔案路徑，自己雙擊打開就好。
