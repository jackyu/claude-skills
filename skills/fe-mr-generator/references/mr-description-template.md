# MR Description Template

產出 MR 描述時依照以下結構。核心原則：MR 是知識載體，不只是變更清單。

送到 review 桌上時就要 review-ready。對 reviewer CP 值最高的區塊是 **概念地圖**（讓人看圖不看 code）。其餘「能從 diff 直接看出來」的資訊（逐項功能、架構選擇、一般 review 重點），就不再花篇幅重複描述——留給程式碼本身。描述只保留 reviewer 難以自行從 code 還原的核心：為什麼、整體輪廓、怎麼測。

## 區塊分級

根據 MR 複雜度決定哪些區塊必填：

| 區塊 | 簡單 MR | 一般 MR | 複雜 MR |
|------|---------|---------|---------|
| 關聯 | ✅ 必填 | ✅ 必填 | ✅ 必填 |
| 為什麼要這樣做 | ✅ 必填 | ✅ 必填 | ✅ 必填 |
| 概念地圖 | — 省略 | ✅ 必填 | ✅ 必填 |
| 做了什麼 | ✅ 必填 | ✅ 必填 | ✅ 必填 |
| 測試說明 | ✅ 簡寫 | ✅ 必填 | ✅ 必填 |
| 截圖 | 視情況 | ✅ 必填 | ✅ 必填 |

> 逐項功能、架構選擇、一般 review 重點、學習點等「diff 看得出來」的內容不進描述——交給程式碼與 reviewer 端的審查工具（fe-mr-review 會自行做風險分流）。開發過程的解題思維（嘗試了什麼、為什麼不行）也不進描述——MR 著重「為何而做、做了什麼」，不需要向 reviewer 完整交代思考過程。

**複雜度判斷**：
- **簡單**：單一元件調整、樣式修改、文案更新、設定檔變更
- **一般**：新增頁面/元件、API 串接、既有功能修改
- **複雜**：架構重構、跨模組影響、效能優化、新技術導入

{{ 用 2-3 句話說明這個 MR 的背景和動機。

   讓不了解需求背景的人也能快速理解 context。 }}

     「動了哪些模組、資料怎麼流、bounded context 的邊界畫在哪」。

    [ 觸發點 ] ──→ [ 模組 A ] ──→ [ 模組 B ] ──→ [ 結果 ]
                      │

    [ 會員清單頁 ] ──→ [ 搜尋篩選 Hook ] ──→ [ TanStack Query ] ──→ [ 列表渲染 ]

## 格式規範

- **禁止出現檔案路徑**：不論相對或絕對路徑，一律用功能描述取代
- **禁止 Markdown 連結格式中包含路徑**：`[文字](src/...)` 這類寫法不允許
- **概念地圖**：純文字 ASCII 箭頭，在 MR 中以程式碼區塊包住保留排版
- **使用繁體中文**
- **MR Title 格式**：見 `references/mr-title-rules.md`（含通用規則與 monorepo 前綴邏輯）
