# 既有專案怎麼漸進導入

新專案直接照 `thresholds.md` 的建議值設 error 就好，這份不用看。

有歷史包袱的專案照建議值一次開下去，會噴出幾百條錯誤。接著發生的事幾乎是必然的：有人把規則關掉，或到處加 `eslint-disable`。**護欄裝了等於沒裝，還多了一堆噪音。**

所以順序是：先量 → 用實際數字設起始門檻 → 只 warn → 確認 CI 綠 → 逐步收緊。

---

## 第一步：量現況

```bash
bash scripts/apply.sh --measure [專案路徑]
```

要量出來的東西：

| 指標 | 為什麼要這個數字 |
|---|---|
| `.ts` 函式長度分佈（p50 / p90 / max） | 決定起始門檻設哪裡 |
| `.tsx` 函式長度分佈 | 同上，但門檻不同 |
| 超過建議值的函式數量 | 判斷「一次修完」是否可行 |
| 最深巢狀層數 | — |
| 超過 200 行的檔案數 | — |
| jscpd 重複率 | 這是最重要的「不得退步」指標 |
| 最高 cyclomatic complexity | — |

---

## 第二步：用量到的數字設起始門檻

判準很簡單：**起始門檻設在「現在最差的值」，讓它不再退步。**

例：`.ts` 最長函式 137 行 → 起始門檻設 140（不是建議的 50）。這聽起來很寬，但它擋住的是「第 138 行以後的每一次膨脹」，而這正是 AI 產出最容易累積的東西。

超標數量決定策略：

| 超標數量 | 怎麼做 |
|---|---|
| 0–5 處 | 直接修掉，門檻設建議值 |
| 6–30 處 | 門檻設在最差值，開 ticket 分批修 |
| 30 處以上 | 門檻設在最差值，**不要開修改 ticket**——之後碰到那些檔案時順手改就好，專門排時間修這種事通常排不進去 |

---

## 第三步：先 warn，不 error

第一版一律 `warn`。目的是讓大家先看到、習慣，而不是立刻卡住工作流。

觀察一到兩週，確認：

- CI 沒有因此變紅
- 警告數量沒有一直往上長

兩件都成立才進第四步。

---

## 第四步：收緊

一次只收一項，收完觀察一週。順序建議：

1. **`max-lines`（單檔）** — 最不痛，違反的地方通常真的該拆
2. **`max-depth`** — 修法直觀，提早 return 就好
3. **`max-lines-per-function`** — 開始有感，但拆函式風險低
4. **`complexity`** — 最痛，常需要重構邏輯，放最後
5. **jscpd 重複率** — 獨立處理，見下

每收一項就把 `warn` 改 `error`，同時把數字往建議值靠一階。

---

## jscpd 的處理不一樣

重複率不適合設固定門檻，適合設「不得退步」：

```
量到目前是 4.2% → threshold 設 4.5%（留一點緩衝）
之後每次降下來，就把 threshold 跟著調低
```

理由：重複率會隨著新功能自然波動，設死了會在無關的 MR 上爆掉。「不退步」是能長期維持的形式。

---

## 什麼時候該放棄某個門檻

不是每個門檻都值得在每個專案裝。以下情況直接跳過，不要硬套：

- **`complexity` 在重表單專案**：多重條件渲染的表單元件破 15 是常態，硬設會變成噪音來源
- **`max-lines` 在有大量 generated code 的專案**：先確認 generated 檔有沒有進 ESLint ignore
- **jscpd 在有大量 config / fixture 的專案**：這類檔重複是正常的，要先設好 ignore 再談門檻

跳過就跳過，**在報告裡明講跳了哪些、為什麼**。裝一半但講清楚，比硬裝全套然後被整包關掉好。

---

## 一個提醒

這整份策略的重點不是「達成漂亮的數字」，是**讓程式碼品質停止退步**。

起始門檻設得很寬也沒關係——它擋住的是從今天開始的每一次膨脹。這比訂一個沒人做得到、三個月後被移除的嚴格門檻有用得多。
