# 互動問答協定

walkthrough 報告產出後，自動進入互動問答迴圈。本文件規範開場、進行中規則、結束條件。

## 開場語

報告末尾固定附上「🚪 進入問答模式」段落：

```markdown
## 🚪 進入問答模式

我已經把這個 MR 讀過一遍，現在你可以直接問我任何問題。回答會用以下標記說明信心：
🟢 高信心（從 code 可推斷）｜🟡 推測（建議跟作者確認）｜🔴 必須問作者

**建議問題**（直接打編號或重新提問）：

1. {從 MR 上下文預測的問題 1}
2. {從 MR 上下文預測的問題 2}
3. {從 MR 上下文預測的問題 3}
4. {從 MR 上下文預測的問題 4}
5. {從 MR 上下文預測的問題 5}

或直接打字提問：例如「為什麼這裡要加 memo？」「這個型別為什麼這樣設計？」「測試夠不夠？」

打 **「結束」** 我會整理「🔴 待詢問作者清單」給你。
```

## 建議問題的選擇

從以下來源預測 reviewer 想問什麼：

1. **🔍 重點區塊白話解釋** 段落中信心標 🟡 的部分（reviewer 容易在這裡有疑惑）
2. **✨ 好做法雷達** 段落中的條目（reviewer 想了解技巧細節）
3. 既有 MR discussions 中已被問過的類似問題（避免重複，但可延伸）
4. [`assets/faq-prompts.md`](../assets/faq-prompts.md) 的常見題庫

## 進行中規則

### 每次回答的結構

1. **信心 emoji**（🟢 / 🟡 / 🔴）開頭
2. **核心答案**（一句話，先回答結論）
3. **延伸說明**（補充細節，引用 code 位置）
4. **後續提示**（若 🔴，提示「已加入待詢問清單」）

### 累積待詢問清單

每次回答 🔴 等級的問題時：

1. 把問題改寫成「可直接複製成 MR comment」的句子
2. 加入內部累積的「🔴 待詢問清單」
3. 在當下的回答後加註：「✅ 已加入待詢問清單」

### 跨問題的脈絡保持

reviewer 連續提問時，後續答案要呼應前面的脈絡。範例：

- Q1: 「這個 hook 為什麼這樣設計？」→ 回答後
- Q2: 「那如果要新增 X 功能要怎麼擴充？」→ 答案要參照 Q1 提到的設計理念

### 跳脫 walkthrough 範圍的問題

若 reviewer 問的問題其實該用其他 skill：

- 「我覺得這段有 bug」→ 建議：「這偏向審查判斷，建議用 `/fe-mr-review` 做完整審查」
- 「這個 MR 寫得真好，幫我做成筆記」→ 建議：「MR 合併後用 `/fe-mr-digest <URL>` 產出完整學習筆記」
- 「整個專案的架構是怎樣？」→ 建議：「這超出單一 MR 範圍，建議用 codebase 探索工具」

但仍嘗試在 walkthrough 範圍內給初步回答。

## 結束條件

以下任一觸發結束流程：

1. reviewer 打「結束」「停止」「夠了」「謝謝」
2. reviewer 開始問與 MR 無關的問題
3. reviewer 主動切換到其他 skill

結束時：

1. 整理「🔴 待詢問作者清單」並輸出（格式見 [`author-roleplay.md`](author-roleplay.md) 結尾）
2. 整理「✨ 好做法勾選清單」並輸出
3. 提示下一步：
   - 若有 🔴 → 「將清單複製到 MR comment 詢問 @{author}」
   - 若有勾選好做法 → 「MR 合併後可用 `/fe-mr-digest <URL>` 寫成筆記」
   - 若還想找問題 → 「用 `/fe-mr-review` 做完整審查」

## 把問題轉成 MR comment 草稿

🔴 等級的問題改寫成 MR comment 時：

| 原始 reviewer 問題 | 改寫成 MR comment |
|---|---|
| 「為什麼這個 MR 沒處理超商付款？」 | 「@{author} 想跟你確認一下，超商付款是規劃在後續 MR、還是這版本暫不支援？如果是後續處理，方便給個預計時程嗎？」 |
| 「為什麼最低訂購金額是 100？」 | 「@{author} `MINIMUM_ORDER_AMOUNT = 100` 是固定商業規則，還是會跟著某些條件變動？想了解一下背景。」 |

改寫原則：

- 開頭 `@{author}`
- 中性、好奇的語氣，不暗示質疑
- 若是想了解背景，明說「想了解一下背景／脈絡」
- 若是建議或質疑，先說脈絡再提建議

## 範例對話流

```
[Walkthrough 報告產出]

🚪 進入問答模式
建議問題：
1. 為什麼把 PaymentMethodSelector 拆成獨立元件？
2. usePayment hook 為什麼放在 features/payments/hooks/ 而不是 hooks/？
3. 這個 MR 為什麼沒處理超商付款？
4. 訂單狀態為什麼從 useState 改成 useReducer？
5. 測試覆蓋率夠嗎？

reviewer: 1

AI: 🟢 PaymentMethodSelector 從原本 inline 在 CheckoutForm 中（約 80 行）抽出來，
從 diff 看呼叫點目前只有 1 處（CheckoutForm），但這個元件有完整的內部狀態管理
（選中項目、hover、validation），語意上獨立成形，符合「抽象化擴用」的判準。
未來如果結帳頁、訂單修改頁、後台都會用，元件已經準備好。

reviewer: 那 3 呢

AI: 🔴 這涉及產品優先序，無法從 code 推斷。
建議直接詢問 @{author}：「超商付款是規劃在後續 MR、還是這版本暫不支援？
如果是後續處理，方便給個預計時程嗎？」
✅ 已加入待詢問清單

reviewer: 結束

AI: [整理輸出 🔴 清單 + 勾選的好做法 + 下一步提示]
```
