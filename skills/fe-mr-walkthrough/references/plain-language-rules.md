# 白話化準則

把技術描述翻譯成 PM / QA 也能讀懂的版本。**讀者畫像**：會用產品、會描述需求、但不寫 code。

## 核心檢查問題

寫完一段白話描述後問自己：

> 「讀完這段，PM 能跟主管解釋這個 MR 在改什麼嗎？」

如果答不出來，重寫。

## 操作規則

### 1. 移除或翻譯框架名詞

| 技術用語 | 白話替代 |
|---|---|
| reducer | 狀態更新規則 |
| memoization / `useMemo` | 記住計算結果避免重算 |
| HOC | 高階元件（一個會回傳元件的函式） |
| Compound Component | 一組搭配使用的小元件 |
| Discriminated Union | 用一個 type 欄位分辨不同形狀的資料 |
| Suspense | 等資料來之前先顯示備案畫面 |
| Server Component | 在伺服器先處理好再送到瀏覽器的元件 |
| Hydration | 把已渲染的 HTML 接管成可互動的 React |
| Race Condition | 兩個任務搶先回來導致順序錯亂 |
| Optimistic Update | 先假設成功、之後再對齊伺服器結果 |
| Tree Shaking | 打包時把沒用到的程式碼丟掉 |

不在表上的：用一句話解釋它是什麼、為什麼出現在這個 MR。

### 2. 用「就像…」類比

抽象概念加類比，幫助讀者錨定：

- 「Promise-level cache 就像門口的雨傘架，已經拿過一支就先放這裡，下次同樣的請求直接取用，不用再跑一趟。」
- 「Discriminated Union 就像信件上的種類戳章——看到『帳單』戳就知道裡面會有金額欄位，看到『廣告』就知道沒有。」
- 「Error Boundary 就像家裡的總開關——某個房間跳電不會把整棟樓拉黑，跳電的房間自己處理。」

### 3. 解釋「為什麼這樣改」而非「改了什麼」

❌ 把 X 從 useState 改成 useReducer
✅ 原本付款流程的狀態零散，改成集中管理後，每個步驟之間的轉換有明確的規則可循，不容易跑到不該到的狀態

❌ 加上 React.memo
✅ 列表裡有 200 個商品卡，原本你每次在搜尋欄打字它們都重畫一次；改完之後只有真正改變的卡片會重畫

### 4. 數字化具體效果

能量化的就量化：

- ✅ keystroke 從 80ms 降到 12ms
- ✅ bundle size 少 12KB
- ✅ 修同類 bug 從 6 處變 1 處

無法量化的用「相對描述」：

- ✅ 比以前少寫一半的 code
- ✅ 新增同類功能不再需要碰到原本的檔案

### 5. 中英文格式

依共用寫作原則：

- 中英文之間加空格：`使用 React Query 管理 API 快取`
- 中文與數字之間加空格：`共 5 個檔案`
- 技術名詞首次出現大寫官方寫法：`TypeScript`、`Next.js`、`Tailwind CSS`

## 反面教材

❌ **過度技術**：「重構 `useOrderForm`，把 `dispatch` 從 props 拉成 context」
✅ **白話版**：「訂單表單原本要靠父層手動把更新動作傳下來，現在改成讓任何子元件都能直接呼叫，少了一層轉手」

❌ **過度抽象**：「優化資料流」
✅ **白話版**：「商品資料原本要過三層元件才到達顯示處，現在只過一層」

❌ **逐字翻譯不解釋**：「discriminated union 讓 TypeScript 能在 switch 中縮窄型別」
✅ **白話版**：「把訂單狀態做成有種類戳章的資料，編譯器看到『付款中』時就知道一定不會有『取消原因』這個欄位，少寫一堆 if 判斷」

## hotspot 解釋的格式

每個 hotspot 用以下三段：

1. **這段在做什麼**（一句話）
2. **為什麼這樣寫**（連結到 MR 意圖）
3. **白話補充**（用類比或量化，給沒寫 code 的人也能懂）
