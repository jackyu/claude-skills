# Code Review 輸出格式範本

使用繁體中文，Markdown 格式，依下列結構產出最終報告。

**撰寫前提**：讀者可能不熟悉本專案架構（含新手）。共用原則見 [`_shared/fe-mr-common/writing-principles.md`](../../_shared/fe-mr-common/writing-principles.md)「審查語氣」一節與 SKILL.md「報告撰寫風格（核心）」——先講脈絡再講問題、每個 finding 配關鍵程式碼、白話先行（第一次術語用「中文 (English)」）、複雜術語放該 finding 末的名詞補充、商業邏輯比喻只放摘要。

節次順序對應 SKILL.md 的 Step 5：Spec 軸 → Standards 軸 → 正確性 → 副作用（爆炸半徑）→ 無害區挑戰 → 前端專項 → 架構與品質門檻合規。**Spec 軸與 Standards 軸照原樣呈現，不與其他節去重、不 rerank**；去重只在「正確性」一節內部做。

```markdown
## Code Review 摘要

**這次改動在做什麼**: [比喻]（就像…）／[技術]（一句精確描述）
**變更規模**: [小型/中型/大型]（[N] 行）
**基準點**: [fixed point]
**整體評估**: [分數]/10 - [一句話理由]

> 大型變更（> 300 行）才加這行。三項判準都不成立時要寫「已評估，不建議拆」，不能省略。
**拆分建議**: [建議拆成 N 份：① … ② …／已評估，不建議拆——理由]

---

## Spec 軸

> 規格來源：[spec 檔路徑 / issue #NNN]
> 無規格時，本節只寫「無規格可對照，本軸未執行」，其餘節照常產出。

### [finding 標題]
- **規格依據**: [引用規格的具體行或段落原文]
- **類型**: 缺漏 / scope creep / 實作走樣 / 不變量破壞
- **位置**: `檔案:行號`
- **說明**: [白話說明哪裡對不上規格、後果是什麼]

**不變量檢查表**（每條都要有結論，不留空）

| 不變量（依規格推導） | 類別 | 結論 | 依據 |
|---|---|---|---|
| [必須恆成立的事實] | 資料一致性 / 狀態機轉移 / 時序 / 錯誤路徑 | 成立 / 破壞 / 無法判定 | [規格行 + `檔案:行號`] |

---

## Standards 軸

> 規範來源：`~/.claude/rules/*.md`、`fe-arch` 檢查清單、專案 `CLAUDE.md`、Fowler smell baseline

### [finding 標題]
- **違反的規範**: [規範檔名 + 具體條目]，或 [smell 名稱]
- **性質**: 硬性違規（明文規範）/ 判斷題（smell baseline）
- **位置**: `檔案:行號`
- **說明**: [白話說明]

---

## 正確性

### [問題 1 標題（用白話描述現象，不用術語當標題）]
- **來源**: [工具 / agent 名稱]
- **嚴重度**: [Critical/High/Medium/Suggestion]
- **位置**: [`檔案:行號`](連結；審 MR 時附 GitLab 行號連結)
- **程式碼**:
  ```tsx
  // 只貼關鍵 3–5 行，省略處用 // …
  ```
- **背景**: [這段程式在做什麼、涉及什麼脈絡；若牽涉既有架構，先簡述該架構在做什麼、為何存在]
- **問題**: [哪裡不對 + 會造成什麼具體後果（如「使用者連點兩次會送出兩筆訂單」）]
- **建議**: [具體、可執行的改進方式]

<details>
<summary>學習點：為什麼這是問題</summary>

[背後原理說明，讓讀者下次能自己看出同類問題；可含改進後程式碼範例]

</details>

> **名詞補充**（若本 finding 出現新手會卡的複雜術語才加；一般常識字不收）
> - **[術語 (English)]**: [一句話：是什麼、為什麼重要]

---

## 副作用（爆炸半徑）

> 每個被改的匯出符號都要出現在表中，即使結論是「diff 外無呼叫者」。

| 被改的匯出符號 | diff 外呼叫點 | 假設是否還成立 | 判定 |
|---|---|---|---|
| `符號名` (`檔案:行號`) | `檔案:行號`（無呼叫者就寫「無」） | [props 契約 / 回傳形狀 / null 行為 / query key / 時序 哪一項受影響] | 未受影響 / 需調整 / 已壞 |

「需調整」與「已壞」的項目，逐則用上方 finding 格式展開說明。

---

## 無害區挑戰

> 挑最不起眼的 hunk 主動破壞。以下 finding 都已經過反駁而未被駁倒。

### [finding 標題]
- **入選 hunk**: `檔案:行號`（為何看起來無害：純搬移 / 預設值調整 / 小條件改動 / 樣式）
- **破壞情境**: [試了什麼，例如「連點兩次送出」「切回視窗觸發 refetch」]
- **結果**: [實際會發生什麼 + 讀碼證據或實跑輸出]
- **反駁與存活理由**: [找過什麼理由說它不會發生、為何該理由不成立]

**已挑戰未破**

| 入選 hunk | 試過的破壞情境 | 為何沒破 |
|---|---|---|
| `檔案:行號` | [情境 1、情境 2] | [防呆位置 / 型別擋掉 / 路徑不可達 + `檔案:行號`] |

## 架構與品質門檻合規

**架構規範**

- [fe-arch 檢查清單結果。檔案位置錯誤 → Minor；高風險域 API 回應缺邊界 `parse()` → Critical]

**靜態品質門檻**

> 門檻數字來源：`fe-guardrails/references/thresholds.md`。
> 每一項都要填數字，**沒超標也要寫**——空著或只寫「無異常」，就分不出是驗過沒事還是沒看。

| 檢查項 | 門檻 | 實測 | 結果 |
|---|---|---|---|
| 函式長度（`.ts`） | 50 行 | 掃過 [N] 支，最長 [M] 行 | 未超標 / [K] 處超標 |
| 函式長度（`.tsx`） | 150 行 | 掃過 [N] 支，最長 [M] 行 | 未超標 / [K] 處超標 |
| 巢狀深度 | 4 層 | 最深 [N] 層 | 未超標 / 超標 |
| 單檔行數 | 200 行 | 最大檔 [N] 行 | 未超標 / [K] 檔超標 |
| 重複邏輯 | 連續 ≥5 行 | [未發現 / N 處] | — |
| 條件複雜度 | 分支數 15 | 最高 [N] | 未超標 / 超標 |

超標的項目逐則用上方 finding 格式展開，附 `檔案:行號`。
