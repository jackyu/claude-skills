# to-acceptance：產生驗收清單

清單是這個功能的人工驗收條件，也是驗收階段 `/verify-acceptance` 逐條跑的依據、MR Evidence 的對照表。格式以 `~/.claude/skills/_shared/acceptance/format.md` 為準，先讀它。

**用法**：`/to-acceptance [issue 號或 spec 檔名]`。沒給就從對話、目前分支名或 mission 名稱推；推不出來就問。

## Step 1：找輸入

| 輸入 | 怎麼拿 | 用途 |
|------|--------|------|
| 主 checkout | `dirname "$(git rev-parse --path-format=absolute --git-common-dir)"` | 清單和 spec 都在 `<主 checkout>/.claude/specs/` |
| spec 檔 | `<主 checkout>/.claude/specs/spec-<iid>-*.md`；找不到就問使用者，沒有 spec 也可以只用 RD 票 | 主要來源：User Stories、Solution、Implementation Decisions |
| RD 票 | `glab api "projects/:id/issues/<iid>" \| jq -r '.title, .description'`（唯讀） | 對照用：票上有「驗收條件」就逐條對照；沒有就拿「實作範圍」和其他具體要求（例：上版順序）對照 |
| 對話 | 這個 session 前面 grill、to-spec 的討論（沒有就略過） | 補規格沒寫、但討論定案的邊界情況 |
| 回歸地圖 | `git -C <主 checkout> ls-tree --name-only origin/main .claude/skills/verify-admin/features/`（client 換成 `verify-client`），內容用 `git show origin/main:<路徑>` 讀 | 判斷回歸要「更新」既有 feature 還是「新增」 |
| 程式碼 | 先 `git -C <主 checkout> fetch origin`，一律讀 origin/main 的版本：`git -C <主 checkout> show origin/main:<路徑>`。功能合併進 main 之前，實作前或實作後跑都一樣 | 寫「改動前」 |
| 專案問題清單 | `git -C <主 checkout> show origin/main:.claude/reference/acceptance-questions.md`；讀不到就改讀 `<主 checkout>/.claude/reference/acceptance-questions.md`；兩者都沒有就只用這份 skill 內建的通用題，不用報錯 | Step 4 的 B：專案特有的漏寫檢查題 |

`git fetch origin` 失敗（網路、權限）就沿用現有的 origin/main，不中斷；完成後在「完成後」摘要裡提一句用的是舊版本。

**key**：照 format.md「檔案與 key」決定。有本 repo 的 RD 票就用票號，不要用 PM 票號。

清單檔已經存在 → 走 Step 5「更新」，不要從頭產。

## Step 2：決定 meta

- `key`：同上
- `mission`：對話或 band 上看得到 mission-band 的任務名（例 `1022-#473`）就填，看不到就省略。沒有 issue 的任務一定要填，mission-band 靠它找到這份清單
- `branch`：spec 或對話已經定了分支名就填，還沒定就省略
- `app`：spec／票改到 `apps/admin` 就是 `admin`，`apps/client` 就是 `client`，兩個都有就是 `both`（每條 AC 要加 `範圍` 欄）
- `branchType`：分支名（或 spec 寫的分支）開頭 `feat_`、`bug_`、`fix_`；看不出來就照需求性質判斷（新功能 `feat`、修 bug `bug`）
- `spec`、`specMtime`：spec 檔名和它現在的修改時間，用下面這行取（macOS、Linux 都能跑，輸出 UTC ISO 8601）：

  ```bash
  python3 -c 'import os,sys,datetime;print(datetime.datetime.fromtimestamp(os.path.getmtime(sys.argv[1]),datetime.timezone.utc).strftime("%Y-%m-%dT%H:%M:%S.000Z"))' <spec 檔>
  ```

## Step 3：拆條目

一條只驗一件使用者看得到（或測試看得到）的事：

- 從 User Stories 和 Solution 取行為；「A 而且 B」拆成兩條
- 不收實作細節（「移除某個 state」「留一行註解」）：那是 code review 的事，不是驗收
- 「其他功能不受影響」這類保證：這次改動的元件裡，有具體可能被波及的畫面才寫成一條（例：同一張表上的側欄按鈕照常能開），每個畫面一條；只是籠統的「其他都不變」就交給驗收階段的整體回歸，不硬寫
- **行為由別的系統負責**（例：排序規則由後端決定、只能在 UAT 驗）：前端這邊只驗「前端沒有干擾」（寫成一般 AC；這條在 mock 下就驗得完整，`驗不了時` 填 `必須驗過`，不是 `只驗前端`）；後端行為另寫一條，前提寫明依賴（例：「後端 #760 已部署到 UAT」），證據**只用** `指令輸出`（存 API 回應，不截圖），操作和預期也寫成打 API 的說法（端點、參數照後端票的契約，例：「依序打 `GET /manual-filing?page=1`、`page=2`」「兩頁接起來未完成全部在前」），改動前寫 `無（新功能）`，回歸標「否」——mock 驗不到真的後端行為；這條的 `驗不了時` 要明確決定是 `可後補｜<等什麼>`（條件真的會到來，先合併）還是 `必須驗過`（擋到環境到位）。`只驗前端` 留給另一種情況：一條 AC 的「預期」本身就混了前端畫得出來、跟後端那一半不在這張票範圍的內容，不好拆成兩條時，只判前端那一半
- 每條 AC 都要有 `驗不了時`，不留空；三個值的意思見 format.md
- 通常 3–10 條；超過 10 條先想想是不是混進了實作細節

每條填欄位（規則見 format.md）：

- **前提／操作／預期**：各一句，具體到可以照著做。預期寫畫面上看得到的字或順序，不寫「正常顯示」
- **改動前**（三選一）：
  - 行為會改變 → 寫既有行為（從 origin/main 程式碼讀；不確定就加 `推測：`）。驗收時拍 Before
  - 確認既有行為不受影響的條目 → `同預期（既有行為不變）`。不拍 Before，只拍 After
  - 全新的行為 → `無（新功能）`。不拍 Before
  - `branchType` 是 `feat` 時，「全新的行為」是預設；但在既有畫面上改東西（例：既有列表加欄位、拿掉按鈕）仍屬於「行為會改變」
- **證據**：畫面看得到 → `截圖（寬度）`（上面「別的系統負責」的條目除外）（admin `1280`，client `375／768／1280`）；畫面看不到的邏輯 → `測試`；兩者都有就都寫
- **驗不了時**：草稿一律先填 `必須驗過`；依賴外部環境的條目留到 4.3 的「需要你決定」，附推薦值一起問使用者，確定要不要改成 `可後補｜<等什麼>` 或 `只驗前端`
- **回歸**：符合任一就標「是」——改動影響 UI 體驗、牽涉商業規則、是新功能；但 mock 驗不到的（真正的行為在後端）一律標「否」。已有同區域的 feature 檔寫「更新 <skill>/<feature>」，沒有寫「新增 <skill>/<feature 檔名，kebab-case>」，再接一句理由。標「是」的條目加 `- 回歸入庫：待寫`
- **來源**：對應 spec 的 User Story 編號或 RD 票的哪一點，多個用頓號串接
- **結果**：一律 `待驗`

## Step 4：逼問

草稿只是「寫了什麼」，不保證「做完」。做法固定：草稿（4.1）→ B 漏寫檢查（4.2）→ A 逐條問（4.3，含 4.2 新增的條目）——這三步一次做完，彙整成**一份輸出**：草稿清單＋覆蓋表、整批列出的自動填答（能從 spec、程式碼、專案清單查到的事實自己查，不要問）、以及「需要你決定」的編號題（業務取捨、範圍決定、要不要等環境這類，每題附推薦答案）。做完就**停下來等使用者回覆**——就算批次項目沒人有意見，也要等這輪回覆才進 4.5 寫檔。回覆裡如果又開出新問題，就再做一輪同樣格式的輸出，直到沒有新問題。

### 4.1 草稿與覆蓋表

列出 RD 票的每一條驗收條件／實作範圍、spec 的每個 User Story，標出對應到哪幾個 AC。對不到的分兩種：屬於實作細節或 Out of Scope 的，寫一句為什麼不收，放進「不在範圍」；其他的留著，等 4.2 看要不要補成 AC。

### 4.2 B：漏寫檢查

讀 spec 和程式碼，判斷**這次改動**（diff／spec 涵蓋的範圍，不是整個頁面）碰到哪些特徵（讀取 API、列表、表單／送出、日期時間、權限、新的後端欄位…），只問用得上特徵對應的題目；頁面上這次沒碰到的既有特徵不問：

| 功能有… | 要問的情況 |
|---|---|
| 讀取 API | 404、其他 4xx、5xx 各顯示什麼 |
| 讀取 API | 401 重新登入，不另外跳錯誤 |
| 讀取 API | 預期中的業務狀態要當資料呈現，不是錯誤（例：資源已被清除、已下架） |
| 讀取 API | 載入中長什麼樣；空資料分清楚 null、空陣列、空字串 |
| 讀取 API | 背景重抓失敗、舊資料還在時怎麼提示 |
| 讀取 API | 畫面停太久資料變舊：切回分頁重抓、定時重抓，還是只靠手動 |
| 讀取 API＋表單 | 編輯到一半背景重抓，已打的值不能被蓋掉 |
| 讀取 API＋寫入 | 拿舊畫面送出被後端拒絕時（例：資料已被別人改過）畫面顯示什麼 |
| 讀取 API | 要不要顯示最後更新時間 |
| 列表 | 分頁時排序在哪一層做；後端重複主鍵；長文字截斷 |
| 表單／送出 | 送出中到換頁前按鈕要鎖；初始值只能有一個來源 |
| 日期時間 | 時區、日期歸屬 |
| 權限 | 角色不對的人看到什麼、會不會被導走 |

再讀 Step 1 拿到的專案問題清單（`.claude/reference/acceptance-questions.md`），逐題檢查適不適用這次的功能；沒有這份清單就只用上面的通用題。

每題能查到答案的（例如「這支 API 有沒有分頁」「401 現在的處理方式」）自己讀 spec、程式碼、專案清單查，不要問。查不到或屬於業務取捨的，列進「需要你決定」，每題附推薦答案。每題的答案只有三種去向：新增一條 AC、併進既有某條的「預期」、寫進「不在範圍」並附理由——寫進不在範圍才有邊界，驗收時不會被追加需求。

### 4.3 A：逐條問（含 4.2 新增的條目）

每條 AC 問四題：

1. 「預期」能不能寫成斷言（「顯示正確」要改成具體的字或順序）
2. 改動前後差在哪：這是新行為，還是要證明舊行為沒變（決定要不要拍 Before、測試要不要紅轉綠）
3. 在哪個環境證明：mock 夠不夠；不夠就記下在等什麼
4. 證明不了時怎麼辦 → 填「驗不了時」欄（`必須驗過`／`可後補｜<等什麼>`／`只驗前端`，見 format.md）

這四題答案一樣併進 4.1-4.3 那份輸出，自己查得到的直接填、查不到的進「需要你決定」，不要另外分批問。

**前提永遠排不出來就拆開，不要發明第四種值**：第 3、4 題如果發現某個前提根本不會到來（例：UAT 不會出現這個狀態），不要硬塞 `可後補`——`可後補` 只用在條件真的會到來的情況。改把這條拆開：能驗的部分留著當 AC，驗不到的部分寫進「不在範圍」並附理由。

### 4.4 問完的判準

每條 AC 的「預期」都寫得成斷言，「證據」的環境和「驗不了時」都填好；4.2 挑中的每題都有去向（新增 AC、併進既有 AC，或不在範圍）。

### 4.5 寫檔

使用者這輪回覆確認（含對批次項目的沉默接受）後才寫檔；回覆裡有新問題就先做下一輪 4.1-4.3 的輸出，等確認完才寫。寫完 Read 回來確認內容。

## Step 5：更新既有清單（規格改過後重跑）

**什麼時候該重跑**：靠 mission-band 提醒——spec 檔在清單定案後被改過，band 會加黃字（`isSpecStale`）。只在對話裡做的裁決抓不到這個提醒，這是已知盲點，使用者要自己判斷重跑。

1. 讀現有清單和新的 spec，逐條比對
2. 內容沒變的條目原封不動，包括結果
3. 內容要改的：保留編號改內容，結果、回歸入庫、整體回歸照 format.md「條目改了之後」處理
4. 不要的：標題改成 `### AC-n（已刪除）<原標題>`，只留來源和 `結果：已刪除｜<今天日期> <原因>`
5. 新的：接在最大編號後面
6. **只對新增或改到的條目跑 Step 4.3 的 A**，Step 4.2 的 B 只檢查這次冒出來的新情況（例：新加了一支讀取 API），一樣整批列出給使用者看。審查階段因 reviewer 意見新增的條目，`驗不了時` 預設 `必須驗過`；舊清單裡沒有「驗不了時」欄的既有條目（還活著、沒被刪除的），這次一起補上（預設 `必須驗過`），一併跑 4.3 第 4 題，跟其他批次項目一起列出
7. meta 的 `specMtime` 更新成 spec 現在的修改時間
8. 把變動摘要（改了哪幾條、刪了哪幾條、新增哪幾條）給使用者確認後才寫檔

## 完成後

告訴使用者：清單路徑、共幾條、幾條要拍 Before、幾條要進回歸、幾條 `驗不了時` 是「可後補」、「不在範圍」收了幾項。還沒拆票的話，接著可以跑 to-tickets，票的驗收條件用 AC 編號引用（例：「AC-1、AC-3」）；已經實作完就直接進驗收。
