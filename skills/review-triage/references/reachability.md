# 可達性複核與操作證據

每筆候選 finding 都照這份判定。內容與 Codex 的 `codex-evidence-review`（`references/failure-probes.md`）同一套標準，兩邊改規則要一起改。

## 一、實務操作可達性複核

判定之前，把技術觸發序列改寫成實務使用者能理解的完整流程，再逐步挑戰：

1. **從實際入口走到結果**：寫明角色、起始頁面或狀態、操作、等待期間、下一步操作與可觀察的損害。不能跳過「使用者怎麼到達這個狀態」，也不能用直接改 props、store、URL 代替實際操作而不揭露。非互動問題改追真實的背景事件、外部輸入或公開 API 呼叫者。
2. **檢查操作當下的防護**：沿 UI、呼叫端、共用模組與後端查遮罩、modal、disabled、導航限制、取消請求、識別檢查、冪等處理。說明哪一層何時生效、有沒有擋住必要步驟。看到遮罩不代表所有輸入路徑都被擋，要查跟這條流程相關的實際操作方式。
3. **核對元件生命週期**：分清同一元件 rerender、卸載後重新掛載、路由換頁、query string 更新。測試保留元件但實際路由會卸載（或反過來）時，不能沿用測試結論；框架行為不確定就標缺口，需要時用瀏覽器驗。
4. **檢查人類操作與時序**：列出必要動作、可用時間窗口與窗口起訖（事件處理、render／commit、遮罩生效、回應到達）。假設要在極短時間內完成多步操作時，要有可行操作或實測依據；同一個 `act`、直接連續呼叫 handler、強制點擊、任意暫停程式，都不算真人做得到的證據。也不設「小於 N 毫秒必不可能」的通用門檻：單一快速連點、已排入的事件、程式自動觸發、慢網路拉長窗口，要依實際路徑判斷。
5. **用反證裁決**：必要操作已證實被擋、又沒有其他具體入口 → 撤銷，必要時改列防禦性建議。缺可達性證據 → 待驗證，附最小下一步，不寫成「實際不可能」。真實流程仍可達 → 確認，說明防護為什麼不夠。

可達性與發生頻率分開判斷：罕見但可達、有實際損害的仍可能要修；高影響但可達性未明的列為合併前待確認。共用或公開模組另有獨立契約或其他真實消費者時，另外驗證違約影響，不能憑某一頁的遮罩排除整個模組的問題。安全問題依攻擊者可控制的入口判斷，不拿一般使用者的 UI 限制代替後端防護。

## 二、確認後的操作證據

UI 可觸發的確認缺陷，用有順序的步驟交代：

- **起始條件**：角色或帳戶、頁面、必要設定與資料狀態，只列觸發需要的
- **操作順序**：用畫面上看得到的按鈕、欄位、分頁名稱，寫清楚點哪裡、輸入什麼、等什麼、再做什麼；不用函式名或「觸發競態」帶過
- **關鍵時機**：要在回應前操作時，說明當下畫面長怎樣、怎麼辨識時機、為什麼還能操作、遮罩或 disabled 為什麼沒擋住。依賴延遲、特定資料或設定要明列；用限速模擬就揭露，不能說成一般網路下已重現
- **可觀察結果**：分開寫預期與實際，用具體值或狀態變化，連到使用者損害
- **佐證層級**：實際 UI 重現附環境、結果、截圖或 log；只由程式控制流證實時，附入口與防護的 `檔案:行號`，明說還沒在 UI 實跑。寫不出完整可行步驟就退回待驗證，不補造流程

測試工具的強制點擊、直接寫 store、呼叫 callback 只能當診斷方式另列。非 UI 問題給等價的真實事件或 API 輸入序列。

## 三、重現層級

| 層級 | 意思 |
|---|---|
| 函式 | 直接呼叫純函式或工具 |
| hook | renderHook、直接操作 store |
| 整合 | 頁面或元件測試，用使用者事件操作 |
| 實際 UI | 真瀏覽器（verify-admin／verify-client drive）走真實入口 |

底層重現不自動證明產品可達。既有測試與實際 UI 的生命週期、防護或時序不同時，寫出差異。
