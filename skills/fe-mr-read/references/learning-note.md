# Phase 3 學習筆記步驟細節

`SKILL.md` Phase 3 各步驟的完整做法。筆記的本質是「學」而非「審」，假設讀者是剛入行 1-2 年的前端工程師，技術概念首次出現時用一句話解釋它是什麼、為什麼重要。

目標是從 MR 萃取四件事：

- **做了什麼**：這個 MR 解決了什麼問題
- **怎麼做的**：工程師選擇了什麼方案，用了哪些技巧
- **為什麼這樣做**：決策背後的考量，包括「為什麼不用其他方式」
- **Reviewer 怎麼看**：資深工程師審查時關注了什麼，提出了什麼見解

## Step N1：盤點 Phase 1 已有的素材

Phase 1 做過的東西直接搬進筆記，不重讀 diff、不重寫：

| Phase 1 產出 | 筆記段落 |
|---|---|
| 📌 一句話總結、🗣️ 白話版描述 | 📋 這個 MR 在做什麼？ |
| 🗺️ 變更地圖 | 🛠️ 整體策略（表格照搬） |
| 🔍 重點區塊白話解釋 | 🛠️ 關鍵實作（改寫成給新手看的解說，程式碼片段沿用） |
| 📊 流程圖 | 📊 流程圖（同一張圖，不重畫） |
| ✨ 好做法雷達（勾選的優先） | ✨ 值得學習的技巧 |
| 🔴 待詢問作者清單 | 🔴 還沒有答案的問題 |

單獨進入 Phase 3（從 `fe-mr-review` 接過來）時，這張表裡的素材只有意圖與變更地圖，其他段落用 Step N2 的分析補上，見 `SKILL.md`「從 fe-mr-review 直接進 Phase 3」。

## Step N2：補 Phase 1 沒做的程式碼分析

### 辨識變更的核心主題

判斷這個 MR 主要在做什麼類型的工作，決定學習重點：

| 類型 | 特徵 | 學習重點 |
|------|------|----------|
| 新功能開發 | 新增檔案、新 component、新 API 串接 | 架構設計、資料流、元件切分 |
| 重構優化 | 檔案重命名、邏輯抽離、結構調整 | Before/After 對比、改善的理由 |
| Bug 修復 | 小範圍精確修改、條件判斷調整 | 根因分析、怎麼定位問題 |
| 效能優化 | memo、lazy loading、快取策略 | 效能瓶頸識別、優化手段 |
| 基礎設施 | config、CI/CD、工具鏈 | 工程實踐、DX 提升 |

### 架構決策（選用）

MR 中若出現符合或違反 `fe-arch` 規範的結構決策（檔案位置、API 三層結構、共用程式碼的提升時機、schema 歸屬），列為「架構決策」類學習點，附上對應的規範條目。判斷不確定時載入 fe-arch 比對，不要自行推測規範內容。

### Before／After 對比

MR 涉及重構或優化時，提取重構前後的程式碼對比，說明：

- 重構前的問題是什麼（可讀性差？耦合高？效能問題？）
- 重構後改善了什麼
- 這個改善為什麼重要

## Step N3：分析 Review 討論

用 Phase 1 抓到的 `--all-discussions` 輸出，不重抓。Review 討論展示了資深工程師的思考過程，是最有價值的學習素材之一。

### 擷取有學習價值的討論

優先擷取：

- **設計層面的討論**：Reviewer 對架構、抽象、介面設計的看法
- **替代方案的探討**：「有沒有考慮過用 X 方式？」→ 作者的回應
- **知識分享型的留言**：Reviewer 補充的背景知識、最佳實踐、踩坑經驗
- **有建設性分歧的討論**：雙方對某個做法有不同意見，最終如何達成共識

忽略：純粹的 typo 修正或格式調整、簡單的 LGTM 或 Approve、與學習價值無關的行政性留言。

### 保留問答脈絡

```
💬 Reviewer（@reviewer_name）:
[Reviewer 的提問或意見，用自己的話整理，但保留核心觀點]

↩️ Author（@author_name）:
[作者的回應，保留關鍵的解釋和理由]

💬 Reviewer（@reviewer_name）:
[如果有後續討論，繼續保留]
```

每段討論後加上「📖 學到什麼」，用一兩句話總結這段討論的學習重點。沒有任何 Review comment 就跳過「Review 精華」段落，不需要特別說明。

## Step N4：推敲「為什麼不這樣做」

從以下線索推敲工程師考慮過但沒有採用的替代方案：

- Review 討論中提到的其他做法
- 程式碼中留下的註解（如 `// 這裡不用 X 是因為...`）
- 從技術經驗推斷合理的替代方案
- Phase 1 問答中 reviewer 問過的「為什麼不用 X」（沿用當時的回答與信心標記）

```
🤔 為什麼不用 [替代方案]？
[解釋為什麼當前方案更適合，替代方案的缺點是什麼]
```

不要為了寫而硬湊，只有在確實有值得討論的替代方案時才寫。

## Step N5：難度與學習標籤

- 難度依 [`_shared/fe-mr-common/difficulty-levels.md`](../../_shared/fe-mr-common/difficulty-levels.md) 標 🟢 初階／🟡 中階／🔴 進階。判斷依據是「讀懂變更需要的前置知識」與「改動範圍」，不是行數。
- 標籤依 [`_shared/fe-mr-common/learning-tags.md`](../../_shared/fe-mr-common/learning-tags.md) 從 12 個標籤中選 1-3 個。不貪多、不取「程式語言」標籤、可新增專案專屬標籤但避免氾濫。

## Step N6：決定筆記狀態

依 Phase 1 記下的 State 欄：

- `merged` → 筆記頭寫合併日期
- `opened`（含 Draft）→ 筆記頭寫「草稿，MR 未合併」，內容可能隨 MR 變動
- `closed` → 筆記頭寫「MR 已關閉、未合併」，並在「📋 這個 MR 在做什麼？」後面加一段「為什麼被放棄」，從討論串與最後幾則留言整理；找不到原因就寫「討論中沒有留下放棄原因」，不要猜

## Step N7：組筆記並寫進 Heptabase

1. 依 [`digest-template.md`](digest-template.md) 組出筆記，段落取捨照該檔的表。
2. 寫進 Heptabase：先 `ToolSearch select:mcp__heptabase-mcp__create_object` 載入工具，再以 `objectType: card` 建卡。內容第一行是 h1 標題，第二行是學習標籤寫成 `#標籤`（`#tag` 會不會自動掛標籤未驗證，掛不上就當一般文字，不算失敗）。
3. **表格一律包在 `<hepta-table tokenId="new" hasColumnHeader="true">…</hepta-table>` 裡**，裸的 markdown table Heptabase 不認，會顯示成一串符號；同一次寫入有多張表就用 `new-0`、`new-1`。每格只能一段行內文字，不能放清單或換行。
4. Heptabase MCP 不在或建卡失敗 → 落到 `<repo 根目錄>/.claude/notes/<project_name>/mr-read-<iid>-<YYYY-MM-DD>.md`，內容同一份但把 `<hepta-table>` 標籤拿掉，變回一般 markdown。`<repo 根目錄>` 取目前工作目錄的 `git rev-parse --show-toplevel`；`project_name` 取 MR 所屬專案路徑的最後一段（例如 `rsc-frontend`），因為被讀的 MR 不一定 checkout 在本機。目錄不在就建，並跟使用者說明落在哪。
5. 建卡或寫檔後 re-read 確認內容有進去（尤其表格有沒有變成真的表格、段落有沒有缺），才回報「已寫入」。

筆記寫完，對話只給 3 句摘要＋卡片標題或檔案路徑，不把整份筆記倒進對話。
