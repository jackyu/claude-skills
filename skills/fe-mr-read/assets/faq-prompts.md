# 預備 FAQ 題庫

預備 FAQ（Step 8）的常見問題題庫。挑選原則：

1. 從 MR diff 與 description 推斷 reviewer 最可能問的 5 題
2. 多樣化信心等級（不要全 🟢，也要有 🟡 / 🔴）
3. 避開既有 MR discussions 已答過的問題（看 `mr-context.sh --all-discussions` 輸出的討論串）

## 通用題庫

### 結構與抽象

- 「為什麼要拆/合這個檔案？」（通常 🟢）
- 「這個 hook 為什麼不直接 inline？」（🟢）
- 「為什麼不用既有的 X 工具/函式？」（🟡，可能有版本／團隊脈絡）
- 「這個元件為什麼要做成 Compound Component？」（🟢）
- 「為什麼放在 `features/X/` 而不是 `components/`？」（🟡）

### 型別

- 「這個型別為什麼要這樣設計？」（🟢）
- 「為什麼用 `unknown` 而不是 `any`？」（🟢）
- 「為什麼要做 discriminated union？」（🟢）
- 「為什麼這裡用泛型，呼叫端會不會更難寫？」（🟢/🟡）

### 效能

- 「為什麼這裡要加 memo？有實際 profile 過嗎？」（🟢/🟡，看是否有 PR 註解）
- 「為什麼用 useDeferredValue 而不是 debounce？」（🟢）
- 「這個 cache 策略有沒有 race condition 風險？」（🟡）

### 錯誤處理

- 「為什麼這裡沒處理 401？」（🟡）
- 「Error Boundary 包在這層的原因？」（🟢/🟡）
- 「為什麼用 try-catch 而不是讓上層處理？」（🟢/🟡）

### 商業邏輯

- 「為什麼 `MINIMUM_ORDER_AMOUNT` 是 100？」（🔴）
- 「為什麼這個 MR 沒處理 X 情境？」（🔴）
- 「這個 timeout 設成 3 秒是後端 SLA 嗎？」（🔴）
- 「為什麼這個欄位要必填？」（🔴）

### 測試

- 「Test coverage 夠嗎？」（🟡 — 建議改用 `/fe-mr-review` 或 pr-test-analyzer agent 做詳細評估）
- 「為什麼這個 case 沒測？」（🟡）
- 「Mock 這樣寫會不會失真？」（🟡）

### 跨系統

- 「後端會怎麼用這個欄位？」（🔴）
- 「這個 MR 跟正在做的另一個 feature 會不會衝突？」（🔴）
- 「上版的 timing 跟後端對齊了嗎？」（🔴）

## 從 MR 內容推斷的特化題庫

依 MR 類型挑選不同重點：

### 新功能（feat）

- 「整體流程是怎麼運作的？」
- 「失敗情境怎麼處理？」
- 「跟既有的 X 功能怎麼整合？」
- 「為什麼選 Y 方案而不是 Z 方案？」（🟡 或 🔴）
- 「下一步預期會做什麼？」（🔴）

### Bug 修復（fix）

- 「根本原因是什麼？」
- 「為什麼之前沒被測試抓到？」（🟡）
- 「會不會引入新的 bug？」
- 「有沒有類似的問題在其他地方？」
- 「需要回去修舊版本嗎？」（🔴）

### 重構（refactor）

- 「重構前的問題是什麼？」
- 「為什麼是現在做這個重構？」（🟡 或 🔴）
- 「會影響到哪些測試？」
- 「行為應該沒變吧？怎麼驗證？」
- 「為什麼不一次重構到位？」（🟡）

### 效能優化（perf）

- 「優化前的瓶頸數據是什麼？」
- 「優化後實際改善多少？」
- 「有沒有 trade-off？（記憶體 vs CPU、bundle size 等）」
- 「會影響其他頁面嗎？」

## 自答品質檢查

每寫完一個自答檢查：

- [ ] 開頭有信心 emoji
- [ ] 結論放在第一句
- [ ] 引用 code 位置（路徑或行號）
- [ ] 🟡 / 🔴 答案有對應的「建議跟作者確認」或「請直接問作者」
- [ ] 沒用禁忌用語（「作者說」「作者認為」）
- [ ] 字數 ≤ 100 字（除非問題本身需要長解釋）

## 反面教材

❌ 全部 5 題都標 🟢（顯得過度自信，且未涵蓋商業／架構層面）
❌ 全部 5 題都標 🔴（沒有發揮 AI 答疑價值）
❌ 答案複製貼上 MR description（沒有理解加值）
❌ 跳過 MR 已 discussions 過的內容直接複用（顯得沒讀過討論）
