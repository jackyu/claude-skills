# Review 報告撰寫原則

供 **review 類 skill**（fe-mr-review、fe-code-review、fe-mr-review-html）共用。語氣為**客觀評判**——指出問題、給後果、提建議。這份與 `writing-principles.md`（欣賞式、給 digest/walkthrough）分工，**不要混用語氣**。

目標：讓「不熟這個專案、甚至剛入行」的工程師也能讀懂報告、快速驗證問題，並順帶學到東西——同時不犧牲對資深讀者的精確度。

---

## 1. 語氣與表達：白話先行、術語走「名詞補充」

輸出的目的是讓人**快速看懂這個變更在幹嘛**，不是寫技術論文，也不是給作者頒獎。寫的時候想像你在跟同事口頭講解，而不是在打考績。

### 語氣

- **不要過度吹捧。** 不用「教科書級」「堪稱典範」「極為優雅」這類誇飾。做得好就簡單講「這裡寫得不錯」「這段處理得很好」就夠了。
- 評價要具體講「好在哪」，但形容詞克制。重點放在做了什麼、帶來什麼好處，不是堆讚美。
- 用口語的自述句，像在跟人說話。不要一句話塞滿縮寫和術語、讀起來像 commit message。

### 技術名詞的處理（最重要）

- 句子**先用白話把事情講清楚**——發生什麼、為什麼好——而且要能獨立讀懂，不依賴讀者已經懂那些英文縮寫。
- 第一次出現的術語用「中文 (English)」格式，例如 `覆蓋率 (coverage)`、`統一入口 (barrel)`。
- 真正需要展開解釋的術語（像 DI factory、blast radius 這種），**不要塞進主句**。主句先講懂，術語放到段落最後的「名詞補充」當作學習素材。
- 一句話最多一兩個術語，超過就拆句。
- 收錄原則：名詞補充只收「新手可能卡住」的術語（如 race condition、hydration、debounce、specificity、backpressure）；一般常識字（API、CSS、function）不收。

### 範例（同一段，改寫前後對照）

❌ 改寫前——全是縮寫，不懂這些詞就完全讀不下去：

> DI factory 把 token 來源 per-broker 留在呼叫端、型別乾淨（readonly / 無 any）、零消費者引用 blast radius 為零、coverage 靠「改從 barrel 入口 import = 貼近真實用法」自然補滿而非硬寫。

✅ 改寫後——先讀懂，術語放最後：

> 這個工廠函式的設計不錯：它沒有把「每一家券商的 token 從哪來」寫死，而是交給呼叫的人決定，所以之後要換券商，不用動到工廠本身。型別也寫得乾淨，該唯讀的有標 `readonly`、全程沒有用 `any` 帶過。另外目前沒有別的地方直接 import 它，所以這次改動影響範圍很小，幾乎不會波及其他檔案。測試覆蓋率 (coverage) 也不是硬湊的——作者把 import 改成從統一入口進來，順帶就貼近真實使用方式，覆蓋率自然就補上了。
>
> **名詞補充**（給想深入了解的人）
> - **工廠函式 / 依賴注入工廠 (DI factory)**：專門負責「產生並組裝好一個物件」的函式，把「要用哪些依賴」的決定集中在一處，方便日後抽換。
> - **影響範圍 (blast radius)**：改一段 code 會波及到的範圍；範圍越小越安全。
> - **統一入口 (barrel)**：用一個 index 檔把多個模組集中 re-export，外部只從這個入口 import。

### 名詞補充的呈現格式（依各 skill 輸出而定）

- **Markdown 報告**：在該段落／該 finding 末放一個「**名詞補充**」清單，不要全部集中到報告最後。
- **HTML 報告**：把名詞補充做成可折疊區塊（`<details>`）或側欄，掛在該段落／該 section 旁。

## 2. 每個 finding 旁邊就附程式碼

- 每個「需要修正 / 觀察」項目，緊鄰處貼**關鍵 3–5 行**程式碼，讓 reviewer 不必另開檔案就看到問題在哪。
- 只取最關鍵的幾行，**不貼整檔 / 整段 diff**；省略處用 `// …` 表示。
- 同時附 **GitLab 行號連結**，要看完整 context 點連結直接跳到該行：
  - 形式：`[`path/to/file.tsx:42`](<web_url>/blob/<branch-or-sha>/path/to/file.tsx#L42)`（blob `#L` 錨點），或 MR diff 連結。
  - `<web_url>` / branch / sha 可從 `mr-context.sh` 輸出的 MR meta 取得。

## 3. 人工 Review 關注用「四欄檢查項」，不要散文

需要人親自確認（程式碼無法自動判斷）的點，一律寫成可勾選檢查項，每項固定四欄：

- **動作**：具體去哪、做什麼（如「在目標 app 開啟登入頁」）。
- **預期**：看到什麼才算對（驗證的判斷基準）。
- **為什麼重要**：不確認會有什麼風險。
- **驗證方式**：怎麼確認（手動點、看 console、跑某指令、問 PD…）。

並標註難度：`(需資深經驗)` 或 `(新手可略過)`，讓不同層級的 reviewer 知道哪些自己能扛。

## 4. 商業邏輯用比喻——但只在導讀、且與技術版並存

- 報告開頭的導讀區（「這個 MR 在做什麼」）用「就像…」的生活化比喻，幫 reviewer 快速建立心智模型、看懂流程與好處。
  - 例：`Promise-level cache 就像門口的雨傘架——第一個人拿過就先放著，後面的人直接拿、不用重買。`
- **比喻不取代精確描述**：導讀同時給「比喻版 + 一句技術版」；進入技術細節區（風險、需要修正）後維持精確用詞，不硬套比喻、不講成童話。
