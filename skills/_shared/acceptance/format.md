# 驗收清單格式

`/to-acceptance` 產生、`/verify-acceptance` 寫回結果、`fe-mr-generator` 填 Evidence、mission-band 讀進度，四方都以這份為準。改格式時四個地方要一起改。

## 檔案與 key

- 清單：`<主 checkout>/.claude/specs/acceptance-<key>.md`
- 證據：`<主 checkout>/.claude/verify-evidence/<key>/`。放主 checkout 而不是 worktree，worktree 被刪掉後證據還在，主 checkout 裡任何 session 都讀得到
- `<主 checkout>`：`dirname "$(git rev-parse --path-format=absolute --git-common-dir)"`。在 worktree 裡也成立
- `.claude/specs/`、`.claude/verify-evidence/` 都不進版控
- **`<key>`**：
  - 有本 repo 的 RD 票（不是 PM 票）：票號數字，例 `473`
  - 有 spec 檔：跟 spec 檔名 `spec-<key>-…` 的 key 一致
  - 都沒有：使用者取的英文短名，只能用 `[a-z0-9-]`，例 `tour-notes`；撞到已存在的檔名就加日期 `1024-tour-notes`
  - mission-band 找清單：任務名裡有 `#<數字>`（例 `1022-#473`、`1022-issue-#473`）就讀 `acceptance-<數字>.md`；其他任務掃 `.claude/specs/acceptance-*.md`，找 meta `mission` 等於任務名的那一份

## 通則

- 欄位值一律單行，不換行
- 符號一律全形：欄位冒號 `：`、分隔 `｜`、括號 `（）`、寬度分隔 `／`、多個回歸目標用 `；`
- 解析時也接受半形 `:`、`|`，但產生時一律寫全形

## 整份結構

以下是虛構的示意，不要照抄內容：

```markdown
# 驗收清單：#901 通知列表加上已讀狀態
<!-- acceptance:meta {"key":"901","mission":"1024-#901","branch":"feat_notice_read_state","spec":"spec-901-notice-read-state.md","specMtime":"2026-10-24T02:10:05.000Z","app":"admin","branchType":"feat"} -->

- 整體回歸：未跑

### AC-1 未讀的通知標題是粗體
- 前提：通知列表有 2 筆，第 1 筆未讀、第 2 筆已讀
- 操作：進入通知列表
- 預期：第 1 筆標題粗體、第 2 筆一般字重
- 改動前：兩筆都是一般字重，看不出已讀未讀
- 證據：截圖（1280）、測試
- 回歸：是，新增 verify-admin/notice-list：已讀狀態是審核人員判斷待辦的依據
- 回歸入庫：待寫
- 來源：#901 驗收條件第 1 點、US2
- 結果：待驗

### AC-2 通知列表的分頁照常運作
- 前提：通知列表有 25 筆
- 操作：點第 2 頁
- 預期：顯示第 21–25 筆
- 改動前：同預期（既有行為不變）
- 證據：截圖（1280）
- 回歸：否
- 來源：US5
- 結果：待驗

### AC-3（已刪除）點通知後自動標成已讀
- 來源：US3
- 結果：已刪除｜2026-10-24 規格改成手動標記，移到 #902
```

## meta

標題下一行，一行 HTML 註解，JSON 欄位：

| 欄位 | 值 |
|------|----|
| `key` | 同檔名的 key |
| `mission` | mission-band 的任務名（例 `1022-#473`）；不知道就省略 |
| `branch` | 功能分支名；還沒建分支就省略，驗收時由 verify-acceptance 補上 |
| `spec` | 產生清單時讀的 spec 檔名（同目錄）；沒有 spec 就是 `null` |
| `specMtime` | 那時 spec 檔的修改時間，UTC ISO 8601、**精確到秒**（毫秒固定 `.000`）。用 `python3 -c 'import os,sys,datetime;print(datetime.datetime.fromtimestamp(os.path.getmtime(sys.argv[1]),datetime.timezone.utc).strftime("%Y-%m-%dT%H:%M:%S.000Z"))' <spec 檔>` 取 |
| `app` | `admin`、`client` 或 `both` |
| `branchType` | `feat`、`bug`、`fix` |

**規格改過的判斷**：spec 檔現在的 mtime 和 `specMtime` 都取到整秒（`Math.floor(ms / 1000)`），前者比較大才算改過。`spec` 是 `null` 就不判斷。

## 整體回歸

`- 整體回歸：` 後面接其中一種：

| 值 | 意思 |
|----|------|
| `未跑` | 還沒跑，或結果已失效 |
| `通過｜<ISO 時間>｜<功能分支 HEAD 的完整 SHA>｜<跑了幾條>` | 例：`通過｜2026-10-24T03:00:00.000Z｜dea29bb649bb1365eca69a8aec0f50c5647a6c37｜3 條 journey`（SHA 寫完整 40 碼，不要截斷）|
| `未過｜<原因>` | |
| `受阻｜<原因>` | 例：沒有 `.env` 起不了 app |

**失效**：寫入方改了任何一條 AC 的結果，或新增、刪除了 AC，就把整體回歸改回 `未跑`。讀取方用 meta `branch` 拿得到功能分支 HEAD 時，HEAD 跟記錄的 SHA 不同也當成 `未跑`。

## 每一條 AC

標題行：`### AC-<n> <一句使用者看得到的行為>`。已刪除的寫成 `### AC-<n>（已刪除）<原標題>`。

- 編號定了就不重排，刪掉的不補號，新的接著往後編
- 已刪除的條目只留 `來源` 和 `結果`

欄位一律 `- <欄位名>：<值>`，順序固定：

| 欄位 | 寫什麼 | 誰寫 |
|------|--------|------|
| 範圍 | 只有 meta `app` 是 `both` 時才有：`admin` 或 `client` | to-acceptance |
| 前提 | 一句，資料或狀態 | to-acceptance |
| 操作 | 一句，使用者做什麼 | to-acceptance |
| 預期 | 一句，畫面上看得到什麼 | to-acceptance |
| 改動前 | 三選一：會改變的行為寫現在的樣子（讀程式碼不確定時前面加 `推測：`）；確認不受影響的寫 `同預期（既有行為不變）`；全新的寫 `無（新功能）` | to-acceptance |
| 證據 | `截圖（寬度）`、`測試`、`指令輸出` 用頓號串接。寬度：admin `1280`，client `375／768／1280` | to-acceptance |
| 回歸 | `否`，或 `是，更新 <skill>/<feature>：<理由>`、`是，新增 <skill>/<feature>：<理由>`；多個目標用 `；` 串接 | to-acceptance |
| 回歸入庫 | 只有 `回歸：是` 的條目才有：`待寫`，或 `已寫｜<repo 相對路徑>、<repo 相對路徑>` | to-acceptance 寫 `待寫`，verify-acceptance 改成 `已寫` |
| 來源 | 對應 issue 或 spec 的哪一條，多個用頓號串接 | to-acceptance |
| 結果 | 見下 | to-acceptance 寫 `待驗`，verify-acceptance 寫回 |

### 結果

狀態詞在最前面，後面用 `｜` 接內容：

| 狀態 | 寫法 | 計數 |
|------|------|------|
| 待驗 | `待驗` | 未完成 |
| 通過 | `通過｜<證據>｜<證據>…` | 通過 |
| 未過 | `未過｜<原因>｜<已拿到的證據>…` | 未過 |
| 受阻 | `受阻｜<缺什麼>｜<已拿到的證據>…` | 未完成（不算過、也不算未過） |
| 待重驗 | `待重驗｜<哪一欄改了>` | 未完成 |
| 已刪除 | `已刪除｜<日期> <原因>` | 不計 |

- **通過的條件**：`證據` 欄列的每一種類型都有對應的證據。缺一種就不是通過，要寫 `受阻`（例：測試過了、截圖因為沒有 `.env` 拍不了）
- 證據寫法：
  - 截圖：`Before <路徑>`、`After <路徑>`，路徑相對於主 checkout，例 `After .claude/verify-evidence/473/AC-1-after-1280.png`；多個寬度各寫一個
  - 測試：`測試 <測試名稱>（紅→綠）`；沒有 Before 的條目寫 `（通過）`
  - 指令輸出：`輸出 <路徑>`，輸出存到證據目錄（例：API 回應存成 `.claude/verify-evidence/<key>/AC-4-response.json`）
- **只有「會改變的行為」拍 Before**：`改動前` 是 `無（新功能）` 或 `同預期（既有行為不變）` 的條目只有 After，測試證據寫 `（通過）`
- 缺少 `結果` 行的條目當成 `待驗`

### 條目改了之後

to-acceptance 更新清單時：

- `前提`、`操作`、`預期`、`改動前`、`證據` 任一欄的文字變了 → 結果原本是 `待驗` 的維持 `待驗`；其他的改成 `待重驗｜<哪幾欄>`；`回歸入庫` 若是 `已寫` 退回 `待寫`；整體回歸改回 `未跑`
- `回歸` 從「是」改成「否」 → 刪掉 `回歸入庫` 行；從「否」改成「是」 → 加 `回歸入庫：待寫`
- 只改 `來源` → 結果不動

## 解析規則（給程式用）

- AC 標題：`^### (AC-\d+)(?!\d)(（已刪除）)?\s*(.*)$`
- 欄位：`^- (範圍|前提|操作|預期|改動前|證據|回歸|回歸入庫|來源|結果)[：:]\s*(.*)$`
- 整體回歸：`^- 整體回歸[：:]\s*(.*)$`
- meta：`<!-- acceptance:meta (\{.*?\}) -->`
- 狀態：值是白名單裡的某個詞，而且那個詞後面緊接 `｜`、`|` 或行尾，才是那個狀態；否則當成 `待驗`（`通過（部分）` 不算通過）
  - 結果的白名單：`待驗`、`通過`、`未過`、`受阻`、`待重驗`、`已刪除`
  - 整體回歸的白名單：`未跑`、`通過`、`未過`、`受阻`，認不得當成 `未跑`
  - 回歸入庫的白名單：`待寫`、`已寫`，認不得當成 `待寫`
- 分隔符 `｜` 和 `|` 都要切
- 認不得的行一律忽略，不要報錯
- `### AC-` 區塊裡沒有 `結果` 行，或結果認不得狀態時，讀取方可以提示「AC-n 的結果格式認不得」，但不要中斷
