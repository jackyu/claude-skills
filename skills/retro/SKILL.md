# Session 回顧與改進沉澱

核心原則：界定素材 → 蒐集訊號 → 四路分診 → 產出提案 → 逐項核可後執行。

**未經使用者核可前不寫入任何檔案，memory 也不例外。** 這是本 skill 最重要的一條，貫穿全程。

## Workflow

### Step 1: 界定回顧素材

素材就是**當前 session 的對話 context**——工具輸出、錯誤訊息、返工、使用者糾正、subagent 回報都算。不去讀 transcript 檔，也不翻其他 session 的記錄。

先列一份客觀清單，只記事實不下評價：

- 本次做了什麼、達成什麼
- 動了哪些檔案（列路徑）
- 觸發過哪些 skill／command／hook
- 派過哪些 agent、各自回報什麼

這份清單是後面所有提案的證據池。**清單裡沒有的東西，不能拿來當提案依據。**

### Step 2: 蒐集改進訊號

掃這五類：

| 類別 | 找什麼 |
|---|---|
| (a) 錯誤與修復 | 跑失敗的指令、驗收抓到的缺陷、後期才發現的問題 |
| (b) 使用者糾正與裁決 | 使用者說「不對、應該是…」的每一處，以及他做過的每個裁決 |
| (c) 繞路與返工 | 做了又改、指示沒送達而重做、誤解規格、方向走偏 |
| (d) 重複提醒 | 同一件事在 session 內講了兩次以上 |
| (e) 機制缺口 | 有 hook／rule／skill 本來可以攔下、卻沒攔下的問題 |

每個訊號記三件事：**發生什麼**（附 session 內的具體證據——引原話或貼指令輸出）、**根因**、**有無機制可預防**。

**沒有訊號就明說沒有。** 一次順利的 session 產出零提案是正常結果。

### Step 3: 四路分診

每個訊號分到一路，**一項提案一個焦點**，不要一次改動多個機制。

**動手分診前先做存在性檢查。** (A)(B)(C) 三路一律先搜既有的 skill、hook、rule 是否已經涵蓋這件事：

```bash
/usr/bin/grep -rn "<關鍵字>" ~/.claude/rules/ ~/.claude/skills/ ~/.claude/hooks/ ~/CLAUDE.md
```

- **查無涵蓋** → 才可以提「新建」。
- **已涵蓋卻還是出事**（規則白紙黑字寫了卻沒被遵守、hook 存在卻沒攔下）→ **不得提新建**。這是既有機制失守，不是缺機制；提案改成「強化既有機制」。

  **強化的力道看失守頻率**，不要一次失誤就開重砲：

  | 失守頻率 | 提什麼 |
  |---|---|
  | **首次**（本 session 第一次，memory 也查不到前例） | 只提最輕量的——**寫 memory 記錄失守情境**，讓後續 session 提高警覺 |
  | **重複**（本 session 內兩次以上，或 memory 已有該規則的失守記錄） | 才提「改措辭補正反例，讓規則更難被忽略」或「升級成 hook 硬閘」 |

  這條呼應 (C) 的「同一件事痛過兩次才立規則」——一次性失誤配重量級提案，就是在違反「不硬湊」那條紅線。

  強化既有規則屬 `~/.claude/playbooks/maintenance.md` 第一節的「改法」，提案中要標明**需使用者核可**。本 skill 全程提案制，這點自然滿足，仍明寫以免誤導。

**(A) skill 提示詞改進** — 指名哪支 skill、哪個段落，附具體修改草稿。改動幅度大的註明「建議走 skill-creator 的 A/B eval 驗證再落地」。

**(B) hook 提案** — 講清楚掛哪個事件（PreToolUse／PostToolUse／Stop／SessionStart…）、腳本要做什麼、有哪個既有 hook 可以當範本。

**(C) rule 提案** — 遵守既有撰寫原則（`~/.claude/playbooks/maintenance.md` 第三節）：同一件事痛過兩次才立規則、每條要有觸發條件＋具體動作＋判準、每檔 ≤40 行。

**(D) memory／學習筆記** — 落點分兩層：

- **前五類**（使用者偏好、環境陷阱、每個 session 都會踩的事、派工與驗證的新模式、只跟單一 repo 有關的）依 `~/.claude/playbooks/maintenance.md` **第二節**的路由表判定。**路由判準以該表為準，當場查，不在此重述。**
- **跨 session 技術教訓** → `~/.claude/skills/learned/<kebab-case>.md`。這條**不在第二節路由表內**，是本 skill 的補充路由。

learned/ 筆記用以下欄位。**這是 retro 的規定格式**——該目錄既有筆記格式並不統一，不要「比照現況」，也不回溯修改舊筆記：

```markdown
---
name: <kebab-case，與檔名相同>
description: <一行摘要>
---

**Extracted:** <YYYY-MM-DD>
**Context:** <在什麼情境下踩到>

## Problem
（寫進症狀關鍵字，日後才搜得到）

## Solution

## When to Use
```

寫任何一筆之前**先搜既有條目**——更新舊的優於新增重複的。

分不進這四路的列進 Step 4 的「不提案」區並說明原因，不要硬塞。

### Step 4: 產出提案報告（僅提案）

每項提案固定七欄：

1. 訊號摘要 ＋ session 內證據
2. 分診類別（A／B／C／D）
3. 落點路徑
4. 具體內容草稿（diff 或全文，要能直接照著做）
5. 預期效益
6. 風險或成本
7. 是否需要走下游工具（skill-creator eval／update-config）

排序：**session 內重複發生 ＞ 曾在其他 session 發生（memory 查得到）＞ 一次性**。

「不提案」區分兩種，**分開列，不要混在一起**：

- **純一次性意外** — 外部服務臨時故障、環境一次性問題之類，沒有可沉澱的機制。
- **既有條目／機制已涵蓋** — 既有 rule／hook／skill／memory 已經妥善涵蓋，本次也沒有失守跡象，不需新增或改動。**附上已涵蓋的出處路徑**（如 `~/.claude/rules/<檔名>.md:<行號>`），讓使用者自行判斷。
  若是「已涵蓋卻仍然出事」，不屬這區——回 Step 3 走「強化既有機制」提案。

**「失守」的判準**：指**行為規範被違背**——規則要求怎麼做、卻沒做到。純描述性的環境事實（某工具有什麼怪癖、某路徑在哪裡）不算失守，那類只要已涵蓋就落在上面第二種，不必提強化。

**本步驟結束前不得寫入任何檔案，memory 也不行。** 這一步的產物就是一份純文字報告。

### Step 5: 逐項核可後執行

用 AskUserQuestion（`multiSelect`）把提案列成選項讓使用者勾選。**核可哪項就做哪項**，沒勾的一律不動，也不要順手多做。

執行時：

- 動 `~/.claude/` 底下任何檔案前先備份，目錄依慣例 `~/.claude/backups/<用途>-<YYYYMMDD>/`（見 maintenance.md 第六節）。
- hook 與 `settings.json` 類改動透過 update-config skill 落地。即使使用者已核可提案，這類改動仍落在 maintenance.md 第一節「動之前必須先問」的範圍，照該節流程走。
- 每執行一項就 read-back 驗證，附上實際輸出再說完成。

retro 的核可門檻比 maintenance.md 第一節更嚴——那裡是「加法可自行、減法與改法要問」，這裡一律要問。從嚴，不衝突。

## 紅線

| 藉口 | 實際 |
|---|---|
| 「這 session 很順，但總得交點東西」 | 沒訊號就報沒訊號；硬湊的提案會稀釋真提案的分量 |
| 「使用者沒抱怨，所以沒問題」 | 返工、繞路、重跑本身就是訊號，不必等抱怨才算 |
| 「memory 只是筆記，先寫了再說」 | memory 也是寫入，一樣要等核可 |
| 「順手把 rule 和 hook 一起改了」 | 一項提案一個焦點，混在一起就無法單獨否決 |
| 「路由表我記得，直接寫上去」 | 落點以 maintenance.md 第二節為準，當場查 |
| 「使用者勾了這項，`settings.json` 就能直接改」 | 仍走 update-config 與 maintenance.md 第一節流程 |
| 「提案越多顯得越用心」 | 提案要有 session 內證據；沒證據的想像不是提案 |
| 「這件事沒人管，立條新規則吧」 | 先搜既有機制；已涵蓋卻出事是失守，要強化既有的，不是再疊一條 |
