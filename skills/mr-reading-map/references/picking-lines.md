# 挑行與排順序

從 `git diff <diff_refs.base_sha> <diff_refs.head_sha>` 挑出要導覽的行。挑的時候同時想兩件事：哪裡值得講、該用什麼順序讀。

## 清單欄位

| 欄位 | 必填 | 說明 |
|------|------|------|
| `order` | 選填 | 導覽順序，字串，見下方。省略＝補充項 |
| `title` | 有 `order` 就必填 | ≤16 全形字、不寫路徑。會變成「接著看」的連結文字和地圖項目 |
| `file` | ✅ | 真實的 repo 相對路徑 |
| `side` | ✅ | `new`（`+` 行）或 `old`（`-` 行） |
| `line` | ✅ | 該 side 的行號 |
| `body` | ✅ | 繁體中文 1–3 句，口語自述，不寫路徑 |

`body` 只寫純內容：不要自己加 `🤖💬`、`[2/5]`、「接著看」尾行或 `<!-- mr:self-annotation -->`，這些在發文時組裝。

## 順序

- **主要點**：`"1"`、`"2"`… 連續，不跳號
- **次要點**：`"2.1"`、`"2.2"`，掛在主要點底下，最多兩層、每個主要點最多 3 個。次要點是獨立的一則 note
- **補充項**：省略 `order`。機械性但值得一提的改動，排在最後發，不掛「接著看」、不進地圖

```
第 1 則 ── 入口點：誰呼叫了這次的核心，讓 reviewer 知道從哪讀進來
第 2 則起 ── 核心由內而外：核心邏輯 → 外圈呼叫端
機械性改動 ── 不發，或標成補充項
```

主要點建議 3–7 則。`order` 只表相對順序，顯示的 `[i/M]` 發文時重算，M＝主要點總數。

## 挑哪些行

只註解 reviewer 從 code 讀不出來的：

- 商業決策（為什麼是這個規則、這個邊界值）
- 不明顯的技術取捨（為什麼不用另一種寫法）
- 魔法數字的來源
- 外部系統的約定（後端契約的隱含假設、第三方 API 的怪癖）
- 刻意不處理的邊界情況，以及為什麼可以不處理

不要註解：code 自己講得清楚的、純風格、import、單純搬移或改名。一個概念只講一次。

## 密度

| 改動規模 | 則數 |
|---------|------|
| 小（單一元件、樣式、文案） | 0–3 |
| 中（新頁面、API 串接） | 3–6 |
| 大（重構、跨模組） | 5–10 |

硬上限 10 則、同一檔最多 3 則，次要點和補充項都算進去。寧可少，不要湊數。

## 行號

- 基準是 `git diff <diff_refs.base_sha> <diff_refs.head_sha>`，跟 GitLab MR 顯示的 diff 完全一致
- 只能註解 `+` 行（`side: new`）或 `-` 行（`side: old`）。context 行 GitLab 會回 400
- 從 hunk header `@@ -old_start,old_count +new_start,new_count @@` 往下數：`+` 行和 context 行讓 new 行號加一，`-` 行和 context 行讓 old 行號加一
- 不確定行號就跳過那則，不要猜
