# 高風險區定義（券商前端）

用於 MR Review 的風險分流。核心理念來自 Relocating Rigor：嚴謹度不會消失，只是換位置——但**有一塊嚴謹不能往兩頭搬**。

> 下單邏輯、金額/股數精度、權限邊界、即時報價一致性、金流狀態機——這幾類 code，AI 一行寫錯就是真實金錢損失。而且它們常常是「業務規則錯」而非「程式語法錯」，linter、type checker、cross-model review **都未必抓得到**。所以：**一般區放心交給自動化 + agent；高風險區，人逐行看，並對齊 spec / PM 業務規則。**

分流原則：**99% 的變更不需要逐行看，1% 的高風險區要看到死。** Review 的第一件事就是把這 1% 找出來。

---

## 五大高風險域

### 1. 下單 / 委託邏輯

寫錯的後果：送出錯誤委託、買賣別反向、數量錯誤、改單/刪單失效。

- **訊號**：變數/函式/檔名含 `order`、`trade`、`委託`、`下單`、`placeOrder`、買賣別（bs / side）、委託類型（限價/市價/IOC/FOK/ROD）、改單刪單
- **常見錯法（前端）**：
  - 買賣別 enum 對應錯（buy/sell 寫反、預設值錯）
  - 委託類型的條件分支漏 case，落到錯誤的 fallback
  - 表單送出未防連點 → 重複下單
  - 數量單位混用（張 vs 股，整股 vs 零股）
- **reviewer 該確認**：買賣別/委託類型的每一條分支是否對應正確業務規則；送出是否有 idempotent 或 disable 防重複；單位換算是否一致

### 2. 金額與股數精度計算

寫錯的後果：金額、手續費、稅金、損益顯示錯誤。

- **訊號**：算術運算 `*` `/` `+` `-` 出現在價格/金額/股數上、`parseFloat`、`Number()`、`.toFixed()`、手續費/交易稅/損益/成本計算
- **常見錯法（前端）**：
  - 直接用 JS `number` 做金額運算 → 浮點誤差（`0.1 + 0.2 !== 0.3`）
  - `toFixed` 當四捨五入用，但它的進位規則與業務要求不一致
  - 整股/零股的最小單位、進位方向沒按交易所規則
  - 先除後乘 vs 先乘後除造成的尾差
- **reviewer 該確認**：金額運算是否走 Decimal 類庫（big.js / decimal.js）而非原生 number；四捨五入/無條件捨去的方向是否符合業務；尾差處理是否與後端一致

### 3. 權限與身份邊界

寫錯的後果：操作到他人帳戶、看到無權限資料、越權操作。

- **訊號**：`account`、`permission`、`role`、`身份`、`分戶`、子帳號切換、feature flag 對應權限、API 帶的帳號識別
- **常見錯法（前端）**：
  - 帳號切換後沿用舊帳號的 query cache / state
  - 權限判斷只做前端隱藏（UI 藏起來但 API 仍可打）
  - 多帳戶情境下，請求帶錯帳號識別
- **reviewer 該確認**：帳號切換時相關 cache/state 是否正確失效；權限是否有對應的後端把關（前端隱藏只是 UX 不是安全）；帳號識別的來源是否單一可信

### 4. 即時報價 / 資料一致性

寫錯的後果：顯示過期報價、部位/庫存與真實值不符、樂觀更新回滾失敗。

- **訊號**：`quote`、`ws`、`socket`、`報價`、`部位`、`庫存`、`optimistic`、WebSocket 訂閱/退訂、輪詢、快取與即時資料合併
- **常見錯法（前端）**：
  - WebSocket 重連後沒重新訂閱，或訂閱沒在 unmount 時退訂 → 記憶體洩漏 / 報價殘留
  - 樂觀更新後 API 失敗，rollback 邏輯漏寫或回滾到錯誤狀態
  - 快取（staleTime）設太長，導致部位/餘額顯示落後真實值
  - 多來源資料（snapshot + 增量推送）合併順序錯亂
- **reviewer 該確認**：訂閱/退訂的生命週期是否對稱；樂觀更新的 rollback 是否完整且狀態正確；報價/部位這類「必須即時」的資料快取策略是否合理

### 5. 金流 / 狀態機

寫錯的後果：狀態流轉錯誤、可執行不該執行的操作、入出金/交割顯示錯誤。

- **訊號**：狀態 enum、status transition、`交割`、`入金`、`出金`、訂單狀態（委託中/部分成交/全部成交/已取消/已刪除）流轉
- **常見錯法（前端）**：
  - 狀態機允許了不該存在的轉移（例如已取消 → 成交）
  - 用字串硬比對狀態，漏掉某些狀態值
  - 依狀態啟用/禁用操作按鈕的條件不完整
- **reviewer 該確認**：狀態轉移是否窮舉且只允許合法路徑；操作按鈕的 enable/disable 條件是否涵蓋所有狀態；是否與後端狀態定義一致

## 升級條件

只要 diff 觸及以上任一域，該段落即標記為「高風險區」，並在 review 輸出最上方的「風險分流」區塊明確列出。高風險區的處理規格：

1. **逐行細看**——不適用「掃讀/抽樣」，每一行都要看
2. **對齊業務規則**——不只看 code 對不對，要回去對 spec / PM Issue，確認業務邏輯本身正確
3. **建議 cross-model 複查**——高風險區另外用不同 model 看一次（例如用 Codex 看 Claude 寫的，反之亦然），不同架構的 blind spot 不同；但 cross-model 仍無法替代「對齊業務規則」這步
4. **驗收標準要明確**——要求 MR 描述附上可驗證的 acceptance 條件，否則退回補充

若 diff 完全未觸及上述任一域，在「風險分流」明確標示「本次無高風險區變更，可採一般審查強度」。
