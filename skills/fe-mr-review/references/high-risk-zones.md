# 高風險區定義（申請／審核前端）

用於 MR Review 的風險分流。核心理念來自 Relocating Rigor：嚴謹度不會消失，只是換位置——但**有一塊嚴謹不能往兩頭搬**。

> 以下五域依目前產品線（證券業申請線上前台／審核管理後台）校準，不是券商前端的通用答案。若團隊之後接手交易、報價這類情境，需要另外定義一份對應的高風險域，不要直接套用這份。

> 身分驗證、審核狀態機、權限邊界、個資處理、多步驟表單完整性——這幾類 code，AI 一行寫錯的後果是核身誤判、案件狀態跑掉、個資外洩，而不只是畫面壞掉。而且它們常常是「業務規則錯」而非「程式語法錯」，linter、type checker、cross-model review **都未必抓得到**。所以：**一般區放心交給自動化 + agent；高風險區，人逐行看，並對齊 spec / PM 業務規則。**

分流原則：**99% 的變更不需要逐行看，1% 的高風險區要看到死。** Review 的第一件事就是把這 1% 找出來。

---

## 五大高風險域

### 1. 身分驗證與文件審核（KYC）

寫錯的後果：核身誤判（該擋的放行、該過的卡住）、證件資料誤讀、審核依錯誤資料通過。

- **訊號**：`kyc`、`ocr`、`身分證`、`證件`、`liveness`、`人臉辨識`、身分證/證件上傳元件、姓名或證號比對邏輯
- **常見錯法（前端）**：
  - OCR 辨識結果未經使用者確認/更正就直接送出
  - 上傳檔案的格式、大小、角度前端沒驗證，辨識失敗仍讓流程往下走
  - 身分證字號、姓名等關鍵欄位比對用鬆散字串比對，全形/半形、大小寫沒 normalize
  - 重新上傳覆蓋舊檔案時，舊檔案對應的審核結果沒有連動失效
- **reviewer 該確認**：OCR/辨識結果是否有使用者確認步驟；上傳檔案的前端驗證規則是否與後端一致；關鍵欄位比對是否有正規化；重新上傳後舊審核狀態是否正確重置

### 2. 審核流程狀態機

寫錯的後果：案件卡在錯誤狀態、可執行不該執行的操作、審核人員看到錯誤的下一步。

- **訊號**：狀態 enum、`status`、`審核狀態`、`送件`、`補件`、`覆核`、`核准`、`退件`、workflow 轉移
- **常見錯法（前端）**：
  - 狀態轉移允許不合法路徑（例如已核准 → 補件）
  - 用字串硬比對狀態值，漏掉某些狀態
  - 依狀態決定操作按鈕（核准/退件/補件通知）的條件不完整，導致審核人員誤操作
  - 多位審核人員併發處理同一案件時，前端沒有版本檢查，後送出的覆蓋先送出的
- **reviewer 該確認**：狀態轉移是否窮舉且只允許合法路徑；操作按鈕 enable/disable 條件是否涵蓋所有狀態；併發編輯有沒有版本衝突處理；前後端狀態定義是否一致

### 3. 申請人與審核人員的權限邊界

寫錯的後果：看到不屬於自己的案件、越權操作、審核人員操作到超出自己權限範圍的案件。

- **訊號**：`role`、`permission`、`審核人員`、`applicant`、`reviewer`、`assignee`、案件指派、API 帶的案件識別/使用者識別
- **常見錯法（前端）**：
  - 切換案件或篩選列表後沿用舊的 query cache/state，混到別人的案件資料
  - 權限判斷只做前端隱藏（按鈕藏起來但 API 仍可直接打）
  - 案件識別（case id）從 URL 帶入時，未檢查是否屬於當前登入者可視範圍
- **reviewer 該確認**：切換案件時相關 cache/state 是否正確失效；權限是否有對應後端把關（前端隱藏只是 UX 不是安全）；案件識別的來源是否單一可信、有沒有做歸屬檢查

### 4. 個資與敏感資料處理

寫錯的後果：個資外洩、敏感資料進日誌、畫面顯示不該顯示的完整資料。

- **訊號**：身分證字號、電話、地址、財力證明等 PII 欄位、`console.log`、錯誤回報（Sentry 等）、URL query string 帶敏感欄位
- **常見錯法（前端）**：
  - 錯誤處理／debug log 把整包表單資料（含身分證字號）印出來或送進錯誤回報服務
  - 敏感欄位用 URL query string 傳遞，留在瀏覽器歷史紀錄
  - 列表/明細頁沒有遮罩處理（只需後四碼時顯示了全碼）
  - 表單欄位的 `autocomplete` 設定不當，讓敏感資料被瀏覽器記住
- **reviewer 該確認**：log／錯誤回報是否過濾敏感欄位；敏感資料是否走遮罩顯示；傳遞方式是否避免進入 URL／瀏覽器歷史；`autocomplete` 屬性設定是否恰當

### 5. 多步驟表單的資料完整性

寫錯的後果：資料遺漏未送出、使用者以為填完但實際少一步、表單改版後舊草稿資料對不上新欄位。

- **訊號**：multi-step form、`wizard`、`draft`、`step`、表單狀態暫存（localStorage/sessionStorage）、分頁式表單導覽
- **常見錯法（前端）**：
  - 使用者跳步或重新整理後，前面步驟填的資料沒有正確保留或重新驗證
  - 草稿儲存的欄位結構跟表單改版後的欄位對不上，舊草稿載入時欄位錯位或遺漏
  - 上一步/下一步導覽沒擋住「必填欄位未完成」就放行跳過
  - 提交前沒有彙總確認頁，或彙總頁資料跟實際送出的不一致
- **reviewer 該確認**：跳步/重新整理後的資料保留與驗證邏輯是否正確；草稿資料結構是否有版本相容處理；步驟導覽的必填檢查是否完整；彙總確認頁資料是否與實際送出一致

## 升級條件

只要 diff 觸及以上任一域，該段落即標記為「高風險區」，並在 review 輸出最上方的「風險分流」區塊明確列出。高風險區的處理規格：

1. **逐行細看**——不適用「掃讀/抽樣」，每一行都要看
2. **對齊業務規則**——不只看 code 對不對，要回去對 spec / PM Issue，確認業務邏輯本身正確
3. **建議 cross-model 複查**——高風險區另外用不同 model 看一次（例如用 Codex 看 Claude 寫的，反之亦然），不同架構的 blind spot 不同；但 cross-model 仍無法替代「對齊業務規則」這步
4. **驗收標準要明確**——要求 MR 描述附上可驗證的 acceptance 條件，否則退回補充

若 diff 完全未觸及上述任一域，在「風險分流」明確標示「本次無高風險區變更，可採一般審查強度」。
