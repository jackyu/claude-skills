# Output Format — Review Mode

依此 skeleton 組裝最終 markdown 報告。撰寫風格見 [`_shared/fe-mr-common/review-writing-principles.md`](../../_shared/fe-mr-common/review-writing-principles.md)：內文維持專業用詞、術語走最後的名詞小辭典、每個 finding 配關鍵程式碼 + GitLab 行號連結、人工 Review 用四欄檢查項、比喻只放導讀。

空區塊（如無一致性問題、無安全疑慮）整段省略，**不要保留空標題**。

```markdown
# MR Review: {標題}

**MR**: {URL} · **作者**: {author} · **類型**: {feature|bugfix|refactor|unknown}
**變更**: {N} 檔，+{add} / -{del}

---

## 🧭 這個 MR 在做什麼

**比喻**：{用「就像…」一句話建立心智模型，幫 reviewer 看懂流程與好處}
**技術**：{一句精確描述實際做了什麼改動}

> ⚖️ 設計判斷（有疑慮才列，否則省略）：值不值得做 / 有沒有更簡單做法 / 什麼會被影響

---

## 風險評估：{🟢 Low | 🟡 Medium | 🔴 High}

| 拉低風險 | 拉高風險 |
|---------|---------|
| {例：純 className 替換、無邏輯改動、build/test 綠} | {例：觸及登入/交割等關鍵流程、非行為等價、需人工視覺確認} |

---

## 🔗 一致性與共用

- **既有類似做法**：[`{file}:{line}`]({連結}) — {專案裡已有的 function/component/pattern}
- **差異**：{這次寫法和既有差在哪，差異是否有意義}
- **建議**：{可否共用既有的；或命名/資料流/檔案位置如何向慣例對齊}

---

## 🔍 發現的問題

### 需要修正（要動作）

#### {問題標題（白話描述現象）}
- **位置**：[`{path/file.tsx}:{line}`]({web_url}/blob/{branch}/{path/file.tsx}#L{line})
- **程式碼**：
  ```tsx
  // 只貼關鍵 3–5 行，省略處用 // …
  ```
- **問題**：{這段在做什麼 + 哪裡有問題 + 具體後果}
- **建議**：{改進方式}

### 🔒 安全性

- {若有：位置 + 漏洞類型 + 可能後果 + 修法（同樣附程式碼/連結）；無則整段省略}

### 技術觀察（不需動作）

- {冗餘但無害、既有差異、低風險項——明確標示「不需在本 MR 處理」}

---

## 👤 人工 Review 需特別關注

> 以下程式碼無法自動判斷，需人親自確認。

- [ ] **{檢查項標題}** `(需資深經驗 | 新手可略過)`
  - **動作**：{去哪、做什麼，如「在 target-app app 開啟登入頁」}
  - **預期**：{看到什麼才算對}
  - **為什麼重要**：{不確認會有什麼風險}
  - **驗證方式**：{手動點 / 看 console / 跑某指令 / 問 PD…}
