# Output Format — Review Mode

依此 skeleton 組裝最終 markdown 報告。撰寫風格見 [`_shared/fe-mr-common/writing-principles.md`](../../_shared/fe-mr-common/writing-principles.md)「審查語氣」一節：內文白話先行、術語走名詞補充、每個 finding 配關鍵程式碼 + GitLab 行號連結、人工 Review 用四欄檢查項、比喻只放導讀。

空區塊（如無高風險區、無安全疑慮）整段省略，**不要保留空標題**。

```markdown
# MR Review: {MR 標題}

**MR 連結：** {URL}
**作者：** {作者}
**MR 類型：** {feature / bugfix / refactor / unknown}
**變更範圍：** {簡述變更了哪些模組/功能}
**檔案數：** {N} 個檔案，+{additions} / -{deletions}

---

## 🚦 風險分流

> 整份 MR 最先看這裡。決定 reviewer 注意力該放哪。

### ⚠️ 高風險區（請逐行細看 + 對齊業務規則）

| 區域 | 觸及的高風險域 | 為什麼高風險 | 需人工/cross-model 確認的點 |
|------|---------------|-------------|---------------------------|
| `{檔案}:{行數}` | {身分驗證/審核狀態機/權限/個資/表單完整性} | {後果} | {確認什麼業務規則} |

<!-- 若無，寫：本次無高風險區變更，採一般審查強度。 -->

### 🟢 一般區

{簡述其餘變更，這些交給自動化 + AI 掃描，不逐行}

---

## 🤖 技術審查結果

### 需要修正

> 只放 review-triage 判成「確認」的 finding。

#### {問題標題}
- **位置**: `{檔案路徑}:{行數}`
- **問題**: {一句話講問題}
- **怎麼重現**: {起始畫面 → 按鈕與輸入 → 時機 → 預期／實際，真人照做就能重現}
- **建議**: {改進方式，一句}
- **佐證**: {「依程式碼推導，未在 UI 實跑」＋入口與防護的 GitLab 行號連結；或「已在本機 UI 重現」＋截圖}

### 想請作者確認

> review-triage 判成「待驗證」的，以及我們質疑做法或前提的。用提問的語氣，不下結論。在高風險區的要寫進合併建議。

- `{檔案}:{行數}` {待驗證：「想確認一下：如果使用者 <操作>，<結果> 會不會……？我從 <入口> 看下去，沒找到擋住的地方」｜質疑前提：「這裡 <行為> 是依據哪份規格或決定？spec 寫的是……」}

### 建議改進

- {防禦性建議標「非阻擋」＋一句理由；純風格只寫 lint 擋不到的}

### ✅ 技術面 LGTM

{如果沒有問題，簡述已確認無誤的項目}

---

## ✅ 合併建議

**結論**：{同意合併 / 有條件合併 / 不同意合併}
**原因**：{一兩句講清楚——基於哪些 finding 或風險。有條件合併要寫「補完 X 即可合」；待人工/跨團隊確認的點也寫在這裡。}

> 只有「需要修正」會讓結論變成有條件或不同意。「想請作者確認」裡落在高風險區的，結論寫「待作者確認後可合」；落在一般區的不影響結論。

## 🔜 後續行動

需要我執行以下操作嗎？
1. **回覆 MR comment** — 將審查建議回覆在 MR 的對應討論串下
2. **執行修復** — 依照「需要修正」項目進行程式碼修改（可全部或選擇性修正）
```
