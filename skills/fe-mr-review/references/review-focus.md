# 各類型 MR 的審查焦點

由 SKILL.md Step R1 依 MR 類型載入。這裡列的是**資深 reviewer 該主動檢查並指出的點**，不是「丟給作者的問卷」。發現問題就直接寫進報告（用白話說明後果），不要只是列一串問句要人回答。

---

## Feature（新功能）

新功能最常見的問題是「重造輪子」和「狀態沒處理完」。

- **有沒有現成的可以用？** 新增的元件 / 邏輯，專案裡是不是已經有類似的？能共用就別重寫（詳見 SKILL.md Step R3）。
- **新東西放對位置了嗎？** 新檔案、新元件的擺放是否符合專案結構，還是隨手放？
- **狀態有沒有處理齊？** 載入中（loading）、出錯（error）、沒資料（empty）這三種狀態，畫面是否都有對應，而不是只做了「資料正常」那條路。
- **新加的套件（package）有必要嗎？** 為了一個小功能引入一整包依賴，是否划算？專案有沒有既有的能達成？
- **會不會影響現有流程？** 這個功能是否動到使用者既有的操作路徑，導致原本能用的東西變了。

## Bugfix（修 Bug）

修 bug 最怕「只壓住表面、沒修到根本」，以及「修這裡、壞那裡」。

- **是治本還是治標？** 這個修法是真的解決了根本原因，還是只是把症狀蓋住（例如多加一個判斷讓錯誤不顯示，但壞資料還是存進去了）？若只能治標，要說明後續怎麼治本。
- **同樣的錯，別處是不是也有？** 這個 bug 的成因（例如某個共用函式沒處理 null），在程式碼其他地方是不是也用了同樣的寫法？要一起檢查，不然修一個漏三個。
- **邊界情境補齊了嗎？** 修正邏輯有沒有漏掉某些輸入情況（空值、極端值、特殊權限）？
- **有沒有防復發的測試？** 是否補了一個會重現這個 bug 的測試，確保以後不會再壞回去。

---

## Refactor（重構）

重構的鐵則：**對外行為必須不變**。改的是內部寫法，不是功能。

- **行為真的沒變嗎？** 重構前後，這段程式的輸入輸出、畫面表現、事件時機是否完全一致？有沒有「順手」改了某個行為（那就不只是重構了，要單獨講清楚）。
- **對外介面相容嗎？** 元件的 props、函式的參數、API 的格式有沒有變？若變了，用到的地方是不是都跟著改了。
- **真的有比較好懂嗎？** 重構的目的是讓人更好維護。如果改完反而更難讀、抽象層更繞，要質疑這次重構值不值得。
- **有沒有過度設計？** 為了「以後可能會用到」而加的彈性，現在用不到的就是負擔（呼應 SKILL.md 三問的「更簡單做法」）。
- **測試還有意義嗎？** 原本的測試如果是綁死實作細節寫的，重構後可能形同虛設，要留意。

## 共通風險點（任何類型都要留意）

1. **只測正常情況**：happy path 過了就當完成，邊界與錯誤情境沒驗證。
2. **隱性依賴**：依賴沒講明的環境、執行順序、權限，換個情境就壞。
3. **跨團隊 / 跨專案沒對齊**：動到共用元件、共用型別、API，卻沒通知會被影響的人，或前後端上線時程沒對好。
4. **文件落後**：程式改了，README / Wiki / API 文件沒跟著更新，下一個人照舊文件做就踩雷。

## 資深同儕的優劣鏡片（跨類型：收斂邊界與介面複雜度）

這組是**跨 MR 類型**都適用的判優劣角度，尤其在 monorepo / 多券商共用（shared-libs）情境。核心信念一句話：**差異與重複都是長期成本；收斂是方向，但要收到對的層。** 以下每條都是「該主動指出的點」，發現就寫進報告，別只丟問句。

1. **差異能不能在源頭消掉？** 看到 broker / 環境專屬分支滲進共用型別或邏輯，先問「這個差異是不是上游（後端 / API 契約）該統一的」，而不是預設前端默默吸收。每多一個分支就是每次改動都要顧的成本；能在源頭抹平的差異，不該在呼叫端長出 adapter。
   - 註：源頭一時改不動時，退而求其次用**更 robust 的通用處理**（如 `nullish` 一次吃 null/undefined），而不是為單一券商寫專屬分支。

2. **這個區分有語意嗎？** `null` vs `undefined`、兩個看似不同其實同義的狀態——**只在它們代表不同意思時才分開處理**。API 回 `null` 與不給 key 若意思相同，就用 `??` / `nullish` 收掉，別製造「假區分」這種假複雜度。判準：先問「區分了之後，哪一段程式會因此走不同路？」答不出來就是該合併。

3. **能不能收成一次？** 連續多筆 state 更新、重複的呼叫、可合併的設定物件——指出來。單看 severity 很低，但它是「作者沒把重複收乾淨」的訊號，累積起來就是雜訊。

4. **共用該收到哪一層（收斂邊界）？** 判斷一段邏輯放 `shared-libs` 還是留 app：
   - **build-time 能自解的 variant（政策、規則資料、`Record<broker>` 這類）→ 往 shared 收**，好處是縮小 export 到 app 的介面、減少 app 端維護面。
   - **app 專屬的 runtime wiring（mutation 注入、機密、per-instance 設定）→ 留 app**。
   - 反過來要警覺：feature 層收斂了、app 的 page / spec 卻各複製一份（逐字相同），是「收斂只做一半」——該再抽一層 wiring hook，或正式承認並排程收尾，不要放著假裝收斂完成。
   - 一句話：收斂的目的是**減少維護面與介面複雜度**，不是「什麼都塞進共用」；收錯層會讓 shared 膨脹或 app 介面變複雜，兩者都算收斂失敗。

5. **姿態：提 preference 要給得出 principle，也接受對方的 principle。** 這是 review *怎麼進行*的原則，不是程式碼本身：
   - 非阻擋級的意見標清楚是 `nitpick`，用「能不能 / 傾向」而非命令句。
   - 分歧用**推理**結案，不靠職級——作者給得出站得住的 rationale（如「縮小 app 介面複雜度」）就收，reviewer 給得出更強的理由作者就改。
   - 拿不準時**參照 repo 既有慣例**當仲裁依據，而非各自堅持風格偏好。

## 資深 reviewer 的實戰關注點（跨專案 review 蒸餾）

這節蒸餾自資深同儕跨多個前端專案、6 個月上百則 review comment 的實戰模式，補齊上面各段沒展開的角度。§1–§7 來自一位以「提問」為武器的 reviewer——**定調他的風格**：低壓語氣（「好奇 / 在想 / 不確定我有沒有理解錯」）但問題極銳利；每則標 severity（`issue` 擋 MR、`nitpick` 看你決定）；要求**證據與真實驗證**，不接受「應該會動」。§8 補上另一位 reviewer 常抓、且前面沒展開的前端框架與規範專屬角度。以下每條都是 reviewer **該主動指出的點**，發現就用白話寫進報告，別只丟問句。

### 1. 錯誤與副作用該在哪一層處理

這是他最密集的關注。核心：**錯誤分類、回報、轉換要收在對的層，別自然地推到太下游各自處理。**

- **回報層級**：能在上游（`apiFetch` / 共用 response parser）判斷分類的錯誤，別推到下游呼叫端各自 try-catch。全域錯誤分類 enum 最適合放共用層——前提是所有 request 都走同一個 `apiFetch` + 共用 parser。
- **重複回報**：上游已 `captureException`，下游又報一次 → Sentry 重複。檢查同一錯誤是否被回報多次。
- **錯誤資訊別失真**：只把 `error.message` 往上丟會遺失結構（status / errorCode）；成功 response 是 `Promise<void>` 或無法 serialize 成 json 的格式時，`.json()` 會噴錯——這類邊界要顧。
- **副作用別塞進 effect / map**：用 `useEffect` 撈資料、在 `.map()` 裡做 side effect、用 effect 處理錯誤，通常放錯位置——撈資料交給 `useQuery`、錯誤交給 `onError`。
- 完整錯誤處理規範見全域 `error-handling.md`；這裡是「reviewer 該指出」的角度。

### 2. 既有基建優先，別另立平行機制 / 把規範沉澱到工具

- **先問能不能併進既有 infra**：新邏輯獨立出來前，先問「不是有 `apiFetch` / 這個 store / `react-hook-form` 了嗎，為什麼不整合進去？獨立的必要性是什麼？」專案裝了的東西幾個 MR 都沒用，是訊號。
- **重複 mechanism 是味道**：兩套登出機制、SPA `useRouter` 與 `location.assign` 混用——指出來並問為何不統一。
- **有標準答案的事沉澱到 CI**：反覆用人工把關的規範（lint、type check、命名），問「能不能在 CI 補檢查」，而非每次 review 用眼睛抓。呼應本 skill 核心哲學：有標準答案的交給工具。

### 3. 一致性擴散：這個模式 / bug / 命名別處是不是也有

- 一個 bug 或限制，檢查是否在其他入口重複（改一個漏三個）；反向，一個好的 transform / util 問「哪些地方也能一起用」。→ 詳見上「Bugfix」段與「優劣鏡片」。
- **命名一致性**：新檔案的 case 慣例（PascalCase / camelCase）是否與既有、與別的 MR 定義一致；隱性字串引用（無 type link、rename 不會報錯）要警覺。

### 4. state / cache 跨頁與使用者輸入

- **初值別用 effect 同步**：`useEffect` 把 prop / 預設值塞進 state 是 bad smell，優先 `useState(() => …)` lazy initializer。
- **存 store 前先想 staleness**：資料存進 store 會遇到跨頁過期；快取（query）重新整理時**會不會蓋掉使用者輸入到一半的值**——這類「即時資料 vs 使用者狀態」的衝突要顧。

### 5. robustness 雙面：別給假安全感，也別過度約束

- **假的安全感**：驗證只保證「目前」情況（如電話格式），會讓人誤以為全面——講清楚涵蓋範圍到哪。
- **邊界 / 空值探測**：習慣性拿極端輸入去戳——空白搜尋要先 `trim`、時區（使用者不在台灣）、`401` 回空陣列合理嗎、「填了但還沒驗證」會不會顯示成「已驗證」。
- **別過度防禦**：把後端的口頭契約寫成硬性 schema、超限直接噴錯，反而平白增加脆弱性；對規格做很多防禦要問原因。
- **fallback 別掩蓋真問題**：硬塞預設值只為過 schema validation、`?? false` 讓缺值恆假——是把 bug 藏起來。

### 6. API 契約與取數職責 / 型別精確

- **HTTP 語意**：`204` / `304` 不該帶 data；狀態碼對應的 body 要符合語意。
- **取數職責歸屬**：分頁 / 排序該交給後端，別 API 分頁了卻只在前端已拿到的那頁排序；留意 n+1 query、能只拿 5 筆就別全撈（over-fetch）。
- **型別精確**：`nullable` vs `optional` 的選擇要一致且有意義（→ 呼應「優劣鏡片」語意精準）；transport 細節寫進 UI 層、缺靜態檢查是危險訊號。

### 7. 收尾品質（各一行，掃到就指出）

- **死碼 / 未使用符號**：宣告了沒用到的常數 / state、永遠跑不到的保底邏輯（如 layout 已先執行）——直接點名刪。
- **實作對齊意圖**：改完意圖是不是反過來了（原本「用戶值優先」變「API 優先」）；多做的東西要問理由。
- **驗證要來真的**：不接受推論——「需要 build 起來測過嗎」「真的觸發一個錯誤看 Sentry 有沒有出現」「這推論需要更多證據」。
- **測試品質**：測試裡別寫實作邏輯、mock 別假裝測到（case 為什麼會過？）、也質疑不值得測的別硬測。
- **MR 衛生**：一個 MR 別混兩件事（如 rc 合併 + issue 改動）；追 code 順手發現的無關疑問標清楚「可先不理」；行為改動附錄影 / 截圖；文件別越長越肥。
- **CSS 副作用**：重構（如拆 `Link`）後 hover / 視覺行為是否非預期改變；置中之類的樣式該收進 ui component 而非散在消費端。

### 8. 前端框架與規範專屬（Next.js App Router / a11y / design token / 相容性）

這組聚焦框架特定與專案規範層，前面幾節較少展開：

- **Next.js App Router robustness**：`useSearchParams()` / `usePathname()` 這類 client hook 沒包在 `<Suspense>` 內，會讓整頁的 static rendering 被 bail-out——要包起來。`loading.tsx` / Shimmer 骨架高度要貼近實際內容，落差大就是明顯的 CLS（版面位移 Cumulative Layout Shift）。Server Component 的 auth gate / redirect 要放在對的層。
- **a11y / ARIA**：自製互動元件（dropdown、tab、modal）要能鍵盤操作（Tab / Enter / ESC）、補對應 `role` 與 `aria-*`（如 `aria-expanded`、`role="listbox"`）；避免兩個同時掛在 DOM 的元件用重複 `aria-label`。優先用既有 `components/ui/`（多半已處理好 a11y）而非自刻。→ 完整規範見全域 `html-semantics.md`。
- **design token 執法**：別 hardcode 色碼（`border-[#DFDFDF]`），改用語意 token（綁團隊的 design-tokens 套件）；連 SVG `fill="#..."` 也儘量改 `currentColor` 隨父層色。多檔同類問題用表格一次點名檔案 / 行號。→ 呼應 §7 CSS 與全域 `tailwind.md`。
- **response passthrough 驗證邊界**：Route Handler 當純透傳 proxy 時，Zod 驗證責任要落在對的層（client `lib/api` vs handler），別「透傳未驗證」又與 MR 描述宣稱的不一致。→ 呼應 §6 契約。
- **helper 抽了卻繞過**：抽了共用 helper（如集中 cookie / header 轉發的 `buildForwardHeaders`）卻在多個呼叫端各自重複實作，會抵銷抽取的意義——要嘛全用、要嘛別抽。→ 呼應 §2 既有基建、§3 一致性。
- **API 演進向後相容**：後端新欄位還沒部署時，前端 schema 用 `nullable().optional()` 避免 crash；內部 package 版本精確釘定、不帶 `^`，避免意外升版帶進 breaking change。
