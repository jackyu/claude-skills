# Comment Polish — 註解整批潤飾

掃描指定範圍內的既有註解，依表達規範提出 before/after 改寫清單，經用戶核可後套用。**只動註解文字，絕不動程式邏輯。**

## 規範來源

改寫判準以 `~/.claude/rules/comment-style.md` 為準，開始前先讀取該檔。若該檔不存在，改用下方內建判準：

- 口語但專業：判準是「這句會不會在台灣的 code review 上被講出來？」不帶玩笑、不帶語氣詞
- 用行為描述取代名詞化黑話；單句超過 40 字就拆開重組
- 砍贅字：「此處」「進行」「用於」「以確保」「該（函式）」「對於…而言」「相關的」「必要的」「值得注意的是」「基本上」
- 避開中國用語（質量、默認、調用、接口、兜底、閉環），用台灣工程圈日常講法

## 工作流程

### Step 1：確定範圍

依用戶指定的檔案、目錄或 diff 界定掃描範圍。未指定時**先問、不自行掃全 repo**，提供選項：

1. 目前分支的變更（`git diff` + `git diff --staged`）
2. 指定目錄或檔案
3. 整個專案（需用戶明確確認才執行）

### Step 2：掃描註解

收集範圍內所有註解（`//`、`/* */`、`#`、JSX `{/* */}`、JSDoc 描述文字），記下 `檔案:行號`。

範圍超過約 10 個檔案時，派 subagent 掃描，主對話只收 `檔案:行號 + 註解原文` 清單。

**跳過不碰**：

- 被註解掉的程式碼（commented-out code）
- License header、shebang
- 工具指令註解（`eslint-disable`、`@ts-expect-error`、`prettier-ignore`、`biome-ignore` 等整行）
- `TODO:`／`FIXME:` 的標籤本身（後面的說明文字可潤飾）
- JSDoc 結構標籤（`@param`、`@returns` 等標籤保留，描述文字可潤飾）

### Step 3：產出改寫清單

逐條對照規範，只列需要改寫的項目，依檔案分組：

```
### src/features/order/api/get-orders.ts

| 行號 | Before | After |
|---|---|---|
| 12 | // 此處進行防禦性檢查以確保資料完整性 | // 先擋掉空值，後面才不用一直判斷 |
```

不需要改的不列。清單後標明總數：「共掃描 N 條註解，建議改寫 M 條」。

### Step 4：核可後套用

用 AskUserQuestion 或直接詢問讓用戶核可，支援「全部套用／挑選部分／全部不改」。核可前不動任何檔案。

套用時逐條用 Edit 修改，只改註解文字：

- 不動任何程式邏輯、字串內容、變數名稱
- 不刪整條註解——該不該存在不是此 skill 的事
- 不新增註解

### Step 5：驗證

1. `git diff` 逐 hunk 確認變動只有註解行；發現非註解行變動立即回報並還原該檔
2. 專案有 type-check 指令時跑一次防呆（如 `npm run type-check`）
3. 回報結果附證據：改了幾條、diff 摘要、type-check 輸出

## 安全邊界

| 規則 | 說明 |
|---|---|
| 只動註解 | 程式邏輯、字串、識別字一律不碰 |
| 先列清單再改 | 未經核可不修改任何檔案 |
| 不刪不增 | 只改寫既有註解文字，不刪整條、不加新註解 |
| diff 驗證 | 套用後用 `git diff` 證明只有註解行變動 |
| 範圍明確 | 未指定範圍先問，不自行掃全 repo |
